# 보조 선처리·Qwen 후속 실행의 2단계 큐 검증

- 구현 기준: origin/develop `b0cb8f0` (화면 통합 포함)
- 작업: codex/two-stage-agent-queues / 별도 native worktree
- 사용자 첨부 [설계](../superpowers/specs/2026-11-19-two-stage-agent-queues-design.md), [구현 계획](../superpowers/plans/2026-11-19-two-stage-agent-queues.md)
- 원래 서비스 checkout·운영 SQLite·기존 방·제공 Qwen/LoRA/judge는 변경하지 않는다. 이번 작업 중 서버를 재시작하지 않는다.

## 구현 범위

보조 해석과 실행을 기존 SQLite에 저장하는 두 단계로 나눴다. 하나의 보조 작업자는 뒤 발화를 미리 처리하고, 하나의 실행 작업자는 최신 방에서 그 원시 구조화 해석을 검증해 후보를 만들고 Qwen이 고른 동일 도구·인자를 실행한다. 참여자별 별도 큐를 만들거나 Qwen 동시 추론을 늘리지 않는다. 기존 run-only fixture 포트는 직렬 호환을 유지한다.

현재 발화·작성자·순서와 과거 문맥의 근거를 보관한다. 명시적인 사실은 재사용하고, 문맥 기준이 바뀐 해석은 실행기가 API를 직접 호출하지 않고 보조 큐로 한 번 돌려보낸다. 최신 정정/취소가 대기하면 오래된 배치의 사실/의무만 순서대로 전달하고 외부 작업·계획을 보류한다.

작업 예약·추출 완료·실행 반영 커서와 상태를 구분했다. 정상 완료한 읽기 checkpoint는 재사용 적합성을 검사하며, 상태 반영·완료 작업·커서는 같은 DB 반영으로 묶는다. 외부 응답을 받기 전 끊긴 읽기 요청의 중복 여부는 알 수 없으므로 외부 API 정확히1회 호출은 보장하지 않는다.

공개 state enum은 유지하고 해석 중·실행 대기 label 및 agent_pipeline을 추가한다. 등록된 작업별 extraction/execution trace가 서로의 active_run_id에 의해 사라지지 않도록 연결한다. 개인 키와 비공개 추론은 trace에 쓰지 않는다. 원시 구조화 batch는 내부 작업 artifact이며 일반 방 API로 노출하지 않는다.

## 검증 구분

1. AI 경계: 원시 해석/최신 grounding 분리, 출처·범위 변조 차단, 명시적 사실 재사용, 문맥 재검토, 실패 시 독립 사실 보존, saved-context retry 호환.
2. 저장: FIFO·공정 배분·준비 창64/8·claim token·서로 다른 커서·중복 apply fence·재시작·방 삭제·완료 읽기 checkpoint.
3. 작업자: 실제 중첩과 실행 직렬화, 최신 취소/정정, 실패 후 진행, 동시 trace, atomic apply 경계 복구 및 상한.
4. 제어된 지연의 세 조건 비교: 기존 직렬+발화별 대기 / 기존 직렬+연속 입력 / 새 큐+연속 입력. 실제 grounding/candidate 코드와 fixture judge/provider를 사용하며 실제 모델 속도나 일반 선택 정확도로 환산하지 않는다.
5. 실제 외부 보조+제공 Qwen+실제 공급자 검증은 별도 격리 DB에서 실행하고, 큐 중첩/동일 인자/취소/반영을 연결해 확인한다.

## 독립 검토

초기 독립 검토에서 발견한 여섯 경계(원문 없는 continuation의 최신 입력 보호, 취소 범위 보존, 과거 cursor 앞의 실패 복구, 활성 snapshot에 checkpoint 혼입, continuation enqueue 전 종료, 완료 후 공개 상태 복구)를 별도 회귀로 검증했다. 재검토에서 발견한 정정 발화·계산 이어가기 경계도 보완하고 재검토 승인을 받았다. 최종 수치와 실제 실행 근거는 아래에 기록한다.

## 실제 서비스 경로 검증

격리 SQLite에서 외부 보조 모델 `gpt-6-luna`과 제공 Qwen·LoRA 및 실제 HTTP 공급자를 사용했다. 14개 검사 모두 통과했다. [검사 목록과 선택·실행 인자](2026-11-19-two-stage-agent-queues.summary.json)

| Qwen이 선택한 도구 | 선택 및 실제 실행 인자 | 실행 경로 |
| --- | --- | --- |
| `search_places` | `{"query": "자산공원", "region": "여수", "category": null}` | HTTP |
| `get_place_details` | `{"place_ref": "kakao:8059512"}` | HTTP |

다음 시각은 첫 보조 추출 시작부터의 경과 시간이다.

| 구간 | 시작 ms | 종료 ms | 상세 HTTP 대기와 겹친 시간 ms |
| --- | ---: | ---: | ---: |
| 장소 상세 HTTP | 6112.5 | 37715.4 | — |
| 영업시간 조회 해석 | 0.0 | 4593.6 | 0.0 |
| 개인 예산 해석 | 6154.3 | 8982.6 | 2828.2 |
| 조회 취소 해석 | 9003.5 | 11738.4 | 2734.8 |

조회·예산·취소 순으로 원문을 보존했다. 개인 예산 150,000원은 소유자 확인 대기로 남았다. 최초 조회는 취소됐고 취소 요청은 완료됐다. 상세 재호출과 계획 반영은 발생하지 않았다.

Qwen이 채점한 3개 결정 중 3개에는 후보가 하나씩 있었다. 이 사례에서 확인한 범위는 원시 점수의 argmax, 선택 인자와 실제 실행 인자의 일치, 실행 및 반영의 연결이다. 여러 후보가 있는 경우의 선택 품질은 별도 검증이 필요하다.

상세 공급자는 동일 장소를 찾았다. 가격·영업시간 항목은 미확인으로 남았다.

## 제어된 세 조건 비교

| 실행 조건 | 장소 검색 호출 | 판정 동시 실행 최대 | 두 번째 발화 해석과 최초 도구 대기 중첩 |
| --- | ---: | ---: | --- |
| 기존 직렬 · 발화별 완료 대기 | 1 | 1 | 없음 |
| 기존 직렬 · 연속 입력 | 2 | 1 | 없음 |
| 2단계 큐 · 연속 입력 | 1 | 1 | 있음 |

세 조건에서 두 예산 제안은 원문 순서대로 각 한 번 반영됐고 조회도 한 건 완료됐다. 기존 직렬의 연속 입력에서는 오래된 반영을 차단한 뒤 누적 발화를 해석하면서 검색을 다시 호출했다. 2단계 큐에서는 최신 입력이 대기하는 동안 준비한 해석을 사용하고 앞선 읽기 결과를 재사용했다. 지연을 제어한 fixture 실행의 시간은 이벤트 순서 확인용이며 실제 서비스 속도 개선을 추정할 근거로 삼지 않는다.

## 범위와 한계

C-revised2 의미 해석 규칙이나 공급자 매칭 정책을 이번 큐 변경에 함께 수정하지 않는다. 두 큐만으로 이전 자연어 누락·가격/영업시간 미확보·계획 미완성을 해결했다고 주장하지 않는다. 원래 Qwen의 yes/no logit 차이와 argmax, LoRA, tokenizer, native judge를 유지한다.

단일 서버 프로세스·uvicorn worker1이 전제다. 여러 프로세스가 같은 큐를 동시에 소비하는 배포는 지원하지 않는다. SQLite를 backlog로 쓰므로 준비 창이 차도 저장된 메시지를 메모리 큐 때문에 버리지 않는다.
