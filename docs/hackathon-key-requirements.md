## 3. 2026년: 모델이 맡아야 하는 역할

### 3.1 원문에 명시된 요구

- 지정된 Qwen을 바탕으로 **판단 성능을 개선**한다. 학습 방식과 보조 모델 결합 방법은 팀이 설계한다. [p.4](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=4)
- 개선한 모델을 서비스의 판단 과정에 연결한다. 발표에서는 **모델 판단이 서비스 실행에 어떻게 연결되는지** 구조도·핵심 기능·실제 동작으로 보여준다. [p.4, 9](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=9)
- 안내된 개선 방법은 SFT, LoRA·전체 미세조정, 선호 학습, 보조 모델 결합, 데이터·설정 개선이다. 방법 이름보다 실제 적용 구성, 개선 전후 결과, 서비스 연결 방식이 중요하다. [p.11](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=11)
- 보조 모델은 분류기·재평가 모델 등으로 Qwen과 연결해 최종 선택에 반영할 수 있다. 종류는 팀이 정하되 평가 입력과 최종 후보 번호 출력은 공통 규격을 따른다. [p.11, 23](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=23)

### 3.2 도구 사용 판단의 의미

| 행동 | 판단 기준 | 여행 Agent에 적용할 수 있는 예시 — 팀 해석 |
|---|---|---|
| 도구 호출 | 필요한 도구와 입력 정보가 충분함 | 지역과 검색 조건을 바탕으로 장소 검색 |
| 추가 질문 | 처리에 필요한 정보가 부족함 | 경로 조회에 필요한 출발지를 사용자에게 확인 |
| 처리 불가 안내 | 제공된 기능으로 요청을 처리할 수 없음 | 예약 도구가 없을 때 실제 예약을 수행할 수 없다고 표시 |

원문은 평가에서 직접 답변 등 다른 후보 행동도 함께 구분한다고 설명한다. 후보 번호를 특정 행동에 고정해서는 안 된다. [p.6, 16](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=6)

### 3.3 개발 적용 해석: 평가 규격과 서비스 구조를 구분

다음은 원문의 요구 범위를 해석한 내용이다.

1. **MCQ 4지선다 출력은 공통 모델 평가의 입출력 규격이다.** 서비스의 대화·조건 추출·도구 인자 생성·계획 갱신 전체를 반드시 4지선다로 구현하라는 요구는 확인되지 않았다. [p.12, 16, 22, 23](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=16)
2. **모든 자연어 생성을 제출한 어댑터 하나가 담당해야 한다는 문구는 없다.** 보조 모델 결합은 명시적으로 허용된다. 다만 개선한 Qwen이 실제 서비스 판단에 어떻게 기여하는지는 보여줘야 한다. [p.4, 10, 11, 23](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=10)
3. 따라서 생성·조건 추출과 행동 판단을 나누는 구조는 검토할 수 있다. 이는 허용된 구성을 바탕으로 한 설계 선택이며, 특정 구조가 대회에서 의무라는 뜻은 아니다.
4. 현재 `submission`의 judge 인터페이스를 Agent에 연결할 때는 후보 생성 방법, 모델이 실제 선택한 행동, 실행된 도구, 실행 결과를 기록하면 서비스 연결을 설명하기 쉽다. **이 기록 방식 자체는 팀의 구현 제안**이다.
5. 평가 실행 중 외부 모델 다운로드나 API 호출에 의존하지 않도록 준비하라는 안내는 제출 평가 실행에 관한 내용이다. 이를 서비스의 지도·장소 검색 API까지 금지하는 규정으로 확대 해석하지 않는다. 서비스의 외부 도구 사용은 발표에서 설명하되, 평가 패키지의 실행 경로와 구분한다. [p.5, 26, 27](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=26)

## 4. 2026년: 평가와 배점

### 4.1 안내된 배점안

원문 p.8의 제목은 ‘평가 배점안’이다. 세부 운영은 최종 공지를 확인한다.

| 심사항목 | 세부 기준 | 배점 |
|---|---|---:|
| 창의성 | 아이디어의 독창성 및 우수성 | 20점 |
| 기술성 | 개발 목표 달성도, Agent 구현 완성도와 시연 안정성 | 30점 |
| 기대효과 및 참여도 | 파급효과, 지속가능성·확장성, 공공성 및 사회적 기여도 | 20점 |
| 발표 전달력 | 발표 내용의 충실성 및 전달력 | 10점 |
| LLM 성능 평가 | When2Call 기반 도구 사용 판단 성능, Macro F1 기준 | 20점 |
| 합계 | 발표·시연 80점 + 객관 평가 20점 | **100점** |

근거: [p.7-8](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=8).

### 4.2 모델 성능 지표

| 지표 | 원문 정의 | 좋은 방향 |
|---|---|---|
| Macro F1 | 행동 유형별 F1을 평균한 주지표 | 높을수록 우수 |
| 정확도 | 전체 문항에서 올바른 후보를 고른 비율 | 높을수록 우수 |
| 도구 환각률 | 도구가 없고 처리 불가가 정답인 문항에서 도구 호출을 고른 비율 | 낮을수록 우수 |

**순위표의 성능 지표와 대회 배점 20점은 다른 점수 체계다.** 객관 평가 20점의 세부 환산 규칙은 최종 공지 사항이다. 임의로 `Macro F1 × 0.2` 등으로 환산하지 않는다. [p.18](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=18)

### 4.3 안내문에 실린 원본 모델 베이스라인

|---|---:|
| Macro F1 | 31.1271점 |
| 정확도 | 48.5411% |
| 도구 환각률 | 36.3636% |
| 평가 문항 | 대회용 MCQ test 377문항 |

원본 베이스라인은 비교용이며 참가팀 순위에서 제외한다. [p.19](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=19)

## 5. 2026년: 데이터와 사용 원칙

### 5.1 제공 자료

| 형식 | 내용 | 용도 |
|---|---|---|
| SFT | 도구 정보·대화와 올바른 응답 | 정답 응답을 따르는 학습 |
| Preference | 같은 상황의 선호·비선호 응답 | 응답 적절성 비교 학습 |
| MCQ | 상황과 응답 후보 4개 | 서버 공통 test의 선택 성능 평가 |

제공 학습 자료는 SFT·Preference이고, 운영 서버의 최종 성능 평가는 MCQ로 진행한다. [p.12](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=12)

| 안내된 파일 | 용도 | 예제 수 |
|---|---|---:|
| `data/train_sft.jsonl` | SFT 학습 | 11,879 |
| `data/dev_sft.jsonl` | SFT 검증 | 1,479 |
| `data/train_pref.jsonl` | 선호 학습 | 7,280 |
| `data/dev_pref.jsonl` | 선호 학습 검증 | 842 |

원본 자료를 **질문 그룹 기준 train 80% / dev 10% / test 10%**로 재분할했다. 서버 test는 MCQ 377문항이다. 파일명·개수는 안내문의 값이며, 현재 작업 폴더에 이 데이터가 모두 존재한다고 검증한 것은 아니다. [p.13](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=13)

### 5.2 지켜야 할 원칙

- train은 모델과 보조 모델 학습에 사용한다.
- dev는 성능 확인과 학습 설정 선택에 사용한다.
- 외부 데이터는 학습에 추가 사용할 수 있다.
- test는 운영 서버에서 보관하고 참가자 자료에 포함하지 않는다.
- **공통 test 문항·정답을 찾아 학습하거나 정답표로 응답하는 방식은 허용하지 않는다.**

근거: [p.14](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=14).

## 6. 2026년: 평가 입출력과 제출 패키지

### 6.1 공통 입출력

- 입력: 사용자 요청을 포함한 대화, 사용 가능한 도구 정보, 응답 후보 4개.
- 출력: 선택한 후보 번호 `0`, `1`, `2`, `3` 중 하나.
- **후보 번호와 행동 유형의 대응은 문항마다 달라진다.**
- p.17의 회의실 예약 사례는 설명용 가상 예시이며 실제 test 문항이 아니다.

근거: [p.16-17](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=16).

JSON 키, JSONL 실행 방식 등 세부 계약은 이 슬라이드만으로 완성하지 말고 **최신 시작 자료의 실행 예제**를 따른다. [p.22](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=22)

### 6.2 패키지에 포함할 내용

모든 팀은 실행 가능한 `submission.zip` 하나를 제출한다.

| 구성 | 포함할 내용 |
|---|---|
| `inference.py` | 모델 로딩, 공통 입력 처리, 후보 번호 반환을 수행하는 추론 코드 |
| `requirements.txt` | 추가 Python 라이브러리와 버전 |
| `weights/` | 실행에 필요한 학습 가중치, LoRA·보조 모델과 관련 설정 |

근거: [p.22](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=22).

| 모델 구성 | 준비할 부분 |
|---|---|
| Qwen 단독 개선 | 공통 모델을 불러오는 추론 코드와 적용한 판단 로직 |
| Qwen + LoRA | LoRA 가중치·설정과 적용 로딩 코드 |
| 전체 모델 학습 | 학습한 Qwen 전체 가중치와 로딩 코드 |
| Qwen + 보조 모델 | Qwen 로딩, 보조 모델·설정, 두 결과 결합 추론 코드 |

근거: [p.23](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=23).

공통 기본 모델 ZIP과 시작 자료 ZIP은 **서로 다른 폴더에 완전히 압축 해제**한다. 기본 모델은 평가 웹에서 별도 제공하며, 자료 개정 시 시작 자료를 다시 받고 모델 파일 변경 여부도 공지를 확인한다. [p.10, 21](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=21)

### 6.3 로컬 점검과 업로드

1. 기본 추론 예제로 입출력을 확인한다.
2. 모델·보조 모델이 저장한 가중치에서 정상 로딩되는지 점검한다.
3. 제출 폴더 기준으로 경로와 추가 라이브러리를 정리한다.
4. 제공된 로컬 검사 도구와 실행 안내로 확인한다.
5. **시작 자료를 압축 해제한 폴더에서** 다음 명령으로 ZIP을 생성한다.

```bash
python tools/make_submission.py
```

6. 평가 웹에서 업로드하고 접수·대기·평가·결과 상태를 확인한다.

이 명령과 도구 경로는 시작 자료 기준이다. 현재 저장소에 `tools/make_submission.py`가 존재한다는 뜻은 아니다. **파일 전송 완료와 채점 완료는 다르다.** [p.24-25](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=24)

### 6.4 제출 제한과 실행 환경

| 항목 | 안내된 규칙 |
|---|---|
| 횟수 | 팀당 하루 5회, 한국 시간 자정 초기화 |
| 동시 제출 | 한 팀의 대기 또는 평가 중 제출은 1개 |

## 7. 2026년: 발표·시연과 준비할 결과물

필요한 결과물은 **모델 실행 패키지, 작동하는 서비스, 발표·시연 자료**다. [p.4](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=4)

발표 권장 흐름은 다음과 같다.

1. 문제와 사용자: 자동화 대상, 기존 처리 과정, 해결할 불편.
2. 서비스 설계: 사용 흐름, Agent 구조, 연결한 도구와 모델 역할.
3. 모델 개선: 사용 데이터, 학습·보조 모델 방식, 비교 실험.
4. 성능 결과: 베이스라인과 제출 성능, 개선한 오류 유형.
5. 실제 시연: 대표 요청의 입력부터 최종 처리 결과까지.
6. 활용 가치: 적용 가능성, 한계, 확장 방향, 팀별 기여.

근거: [p.9, 27](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=27).

발표 전에는 최종 평가 완료·점수, 발표 모델 버전과 서비스 모델 버전, 데이터·개선 방법·실험 결과, 발표와 시연의 일치, 서비스 실행 방법, 팀원별 역할을 확인한다. [p.28](./2026_AI_Agent_Hackathon_Orientation-1.pdf#page=28)

**팀 개발에 적용할 우선순위 — 해석:** 모델 점수만 높이는 작업과 별개로, 실제 Agent가 판단하고 도구를 실행해 결과를 갱신하는 흐름을 끝까지 작동시켜야 한다. 기술성 30점에는 구현 완성도와 시연 안정성이 포함된다. 화려한 화면이나 특정 웹 프레임워크가 필수라는 요구는 이 안내문에서 확인되지 않았다.

## 10. 우리 팀의 개발·제출 체크리스트

아래는 대회 원문을 바탕으로 만든 팀 작업 목록이다. FastAPI·SSE·지도 API·화면 구성·trace 형식은 팀의 선택이며 대회 지정 기술이 아니다.

- [ ] 개선한 Qwen이 선택한 행동이 실제 Agent 실행에 연결되도록 구현한다.
- [ ] 생성·조건 추출·행동 판단·도구 실행에서 각 모델과 코드의 역할을 설명할 수 있게 정리한다.
- [ ] 모델 입력, 선택 결과, 도구 호출과 결과를 남겨 발표·오류 분석의 근거로 쓴다.
- [ ] 서비스 시연용 실행 경로와 MCQ 평가용 제출 경로를 구분해 점검한다.
- [ ] 제출 패키지는 평가 중 외부 모델 다운로드·API 호출 없이 필요한 추론을 수행하도록 준비한다.
- [ ] 원본 비교값, 우리 팀 dev 실험, 실제 서버 제출 점수를 서로 구분해 기록한다.
- [ ] 발표에 사용하는 모델 버전과 서비스·제출 패키지의 버전을 기록한다.
- [ ] 대표 사용자 요청부터 도구 실행·상태 갱신·최종 결과까지 시연한다.
- [ ] 제출 전 로딩·경로·의존성·입출력을 로컬에서 확인한다.
- [ ] 업로드 후 평가 완료 상태와 최종 점수까지 확인한다.
- [ ] 2025년 일정·배점·발표 시간·제출 요건을 2026년 요건에 섞지 않는다.
