# 도구별 준비조건·불확실성 표시·Qwen 선택 개선 설계

- 작성일: 2026-11-19
- 상태: 대화에서 합의한 방향을 정리한 설계안. 이 문서는 구현·검증 완료 보고가 아니다.
- 적용 기준: `codex/qwen-judge-tool-execution`, 구현 기준 커밋 `c6c928f`와 이후 확인한 동작.
- 보존 대상: 제공된 Qwen·LoRA·토크나이저·judge 채점 방식, 기존 DB·대화방·사람의 확인 기록.
- 현재 작업 범위는 문서 작성이다. 제품 코드·환경 설정·DB·서버는 변경하지 않는다.

## 1. 목적과 기존 설계와의 관계

도구 실행에 필요한 정보와 여행안 최종 확정에 필요한 정보를 분리한다. 장소가 언급되면 필요한 조사를 진행할 수 있고, 정보가 일부 부족해도 확인된 일정·비용을 초안으로 보여준다. 확인되지 않은 값과 미처리 요청은 결과에 남기며, 사람의 동의나 최종 확정으로 바꾸지 않는다.

이 문서는 [보조 모델 문맥 보완과 Qwen 최종 행동 선택 설계](2026-11-18-minimal-tool-inputs-design.md)의 후속 설계다. 역할 분담·후보 부족 예외·Qwen 원본 채점 유지 원칙은 계승한다. 기존 문서의 다음 제한은 이번 설계로 대체한다.

- 일정과 비용에 공통으로 적용하던 전체 계획 준비조건을 도구별 조건으로 나눈다.
- 기존 상세 조회 중심 요청을 조회 목적·대상별 처리로 확장한다.
- 하나의 `needs_input`이나 실행 종료로 표현하던 미완료 상태를 요청별 진행·오류·질문으로 구분한다.
- 기존 반환값·캐시를 무조건 유지한다는 제한은 필요한 부분 결과·매칭 상태·캐시 적합성 보완에 한해 대체한다.

새로운 Agent 프레임워크, 별도 워크플로 서비스, 추가 진단 API, 예약·결제 기능은 도입하지 않는다. 기존 LangChain·실행기·방 저장 구조·화면 패널을 활용한다.

### 접근 방식

| 검토한 방식 | 판단 |
| --- | --- |
| 기존 전역 준비조건을 유지하고 프롬프트만 수정 | 부분 계산 차단·질문 소실·공급자 매칭 문제를 해결하지 못한다. |
| 보조 모델이 도구 실행까지 담당 | Qwen만 최종 도구를 선택한다는 요구에 맞지 않는다. |
| 보조 모델은 의미를 구조화하고, 코드는 도구별 유효 후보를 구성하며, Qwen이 최종 선택 | 채택한다. 실행 가능한 조사와 최종 확정 검증을 분리할 수 있다. |

## 2. 유지할 경계

| 구성 요소 | 책임 |
| --- | --- |
| 외부 보조 모델 | 현재 발화·관련 문맥에서 요청·장소·조건·찬반·정정·취소·누락 정보를 근거와 함께 구조화 |
| 서비스 코드 | 문맥 조회, 근거·소유권 검증, 대상 해소, 인자 조립, 도구별 준비 판정, 실제 후보 구성 |
| 제공 Qwen + LoRA judge | 전달받은 실제 후보를 기존 방식으로 평가하고 최종 선택 |
| 기존 도구 실행기 | 선택된 동일 호출을 재검증해 실행하고 실제 관측·부분 결과·오류 반환 |
| Backend | 버전·작성 권한 검사, 결과 저장, 동의·확정 처리, 화면용 상태 제공 |
| Frontend | 저장된 결과·동의·불확실성·진행 상태 표시와 사람의 선택 전달 |

보조 모델에 도구 실행 권한·최종 도구 순위·정답 후보 지정을 맡기지 않는다. Qwen의 원시 점수는 확률이나 사람의 동의 수준으로 표시하지 않는다.

다음 검증은 유지한다: 원문·작성자·조건 소유권, 방 내부의 실제 장소 참조, 유효한 수량·금액·시간, 활성 항목 버전, canonical 계산 인자 일치, live/fixture 근거 구분, 최종 확정 권한.

## 3. 전체 처리 흐름

```text
현재 발화 저장
→ 현재 발화·작성자·최소 방 상태·열린 질문 확인
→ 명백한 단독 잡담이면 새 작업 없이 종료
→ 1차 보조: 요청·사실·근거·미해결 내용 구조화
→ 필요한 정보의 출처 분류
   ├ 과거 대화에 있음 → 관련 기록만 조회하고 필요할 때 2차 보조
   ├ 선행 관측이 필요함 → 해당 선행 도구의 후보 준비
   └ 사람이 새로 정해야 함 → 필요한 질문 후보 준비
→ 목적·대상별 실행 가능한 호출과 응답 후보 구성
→ Qwen 최종 선택
→ 실행 직전 유효성 재확인 → 같은 인자로 실행
→ 실제 결과·미확인 정보·대상별 진행 상태 반영
→ 남은 요청이 있으면 새 관측으로 다음 판단 회차 진행
```

‘Qwen 1회’는 한 판단 회차에서 문맥을 보완한 뒤 최종 비교를 한 번 한다는 뜻이다. 후보마다 독립 forward를 수행하는 원본 judge는 유지한다. 검색 뒤 상세 조회처럼 새 관측이 필요한 연쇄 작업은 다음 회차에서 다시 선택한다.

‘응’, ‘아니 15만원’, ‘거기는 빼자’는 짧아도 답변·정정·반대일 수 있다. 열린 질문과 대상을 확인하기 전에 잡담으로 버리지 않는다. 기존 회차 한도 안에 끝나지 않은 요청은 저장하고, 기존 후속 실행 경로에서 재개한다. 무한 실행 루프는 만들지 않는다.

## 4. 보조 출력과 근거 검증

### 4.1 이미 구현된 기능과 보완할 내용

현재 `ExternalAuxiliary`는 LangChain `with_structured_output(AuxiliaryBatch, method="json_schema", strict=True)`와 Pydantic 검증을 사용한다. Structured Output을 새로 도입하는 작업은 아니다. 스키마와 의미 검증을 보완한다.

| 정보 | 처리 원칙 |
| --- | --- |
| 요청 | 조회·계획·비용·미지원 행위 등을 목적별로 구분. 요청·정정·취소를 구분하고 원문에 연결 |
| 장소 | 이름·제외 이름·근거를 보존. LLM이 공급자 ID를 생성하지 않음 |
| 조회 내용 | 단순 위치 검색인지, 상세·가격·영업시간 요청인지 구분 |
| 조건 | 작성자·대상·값·정정 대상을 보존. 예산은 KRW 정수로 정규화 |
| 찬반 | 대상 항목·작성자·현재 항목 버전·명시적 표현에 연결 |
| 미해결 내용 | 필요한 정보와 출처를 구분하고, 해결 근거가 생길 때만 제거 |

기존 `item_proposals`, `constraint_proposals`, `support_observations`, `analysis.requests`를 재사용한다. 요청은 도구명 대신 사용자의 목적을 나타내도록 확장하고, 기존 저장 요청 `intent=place_details`는 기존 의미로 읽을 수 있게 한다. 새 스키마의 정확한 필드명은 구현에서 FE·BE·AI 계약을 함께 맞추되, 아래 의미는 필수다.

- 조회와 방문 제안은 별개다. ‘찾아줘’만으로 방문 희망·찬성을 만들지 않는다.
- 목적·대상이 여러 개면 기존 요청 목록에 나눠 보관하고 같은 원문 메시지로 묶어 표시한다. 이미 저장된 다중 대상 요청도 대상별로 진행하며 전체 참조를 비우지 않는다.
- 장소 참조가 없어도 이름과 원문 근거를 유지한다. 장소 ID가 없는 상태를 검색 불가능으로 취급하지 않는다.
- 취소는 작성자의 기존 요청과 명확하게 연결한다. 대상이 모호하면 확인하고 다른 사람의 요청을 임의로 취소하지 않는다.

### 4.2 검증과 병합

‘내 예산은 15만원이야. 4시까지 귀가한다는 뜻은 아니야’는 예산 `150000`과 귀가 제한 부정으로 분리한다. 문자열 정규화 전후의 출처를 보존하고, 문장 전체 부정 규칙으로 정상 예산을 거절하지 않는다.

짧은 인용만 보지 않고 해당 대상에 걸리는 문장·부정·정정 범위를 확인한다. ‘한강공원 좋아하지 않아’에서 ‘한강공원 좋아’만 인용해 찬성으로 통과하면 실패다. 기존 원문 추가 검사도 유지하며, 모든 인용 경로가 안전하다고 가정하지 않는다.

과거 기록은 현재 요청을 해소하는 근거다. 과거 찬반을 현재 작성자의 새 찬반으로 재등록하지 않고, 최신 명시적 제외·정정을 우선한다. ‘내가 고른 두 곳’의 기록 조회는 기존 검색 관측이 있어야만 가능하도록 제한하지 않는다.

2차 보조는 기존 사실·요청·누락 항목을 근거별로 병합한다. 2차가 어떤 항목을 출력하지 않았다는 이유만으로 해결됐다고 판단하지 않는다. 제안된 값의 유효성 검사와 복합 발화의 추출 누락 검증은 별개로 수행한다. Structured Output만으로 완전한 추출을 보장한다고 주장하지 않는다.

저장된 열린 질문도 동일하게 취급한다. 새 결과의 질문 목록이 비어 있다는 이유로 기존 질문을 삭제하지 않는다. 답변·연결된 요청의 취소·근거 있는 문제 해소처럼 닫을 이유가 있어야 하며, 이미 답변한 기록은 보존한다.

## 5. 요청과 후보 구성

### 5.1 ‘찾아줘’ 처리

‘돌산공원하고 자산공원 찾아줘’는 조회 요청 두 대상으로 처리한다.

1. 이름과 방의 지역으로 각각 `search_places` 후보를 만든다.
2. Qwen이 선택한 검색을 실행하고 결과를 표시한다. 단순 위치 검색이면 불필요한 상세 수집을 이어가지 않는다.
3. 가격·영업시간·상세 정보 요청이면 장소가 식별된 뒤 `get_place_details` 후보를 만든다.
4. 실제 지점이 여러 개여서 상세 대상을 정해야 한다면 관측된 선택지와 구체적인 질문을 제시한다.

한 대상이 이미 식별되고 다른 대상이 새 이름이면 요청한 정보에 맞춰 독립 처리한다. 단순 위치 조회는 적합한 기존 검색 결과를 재사용·표시하고 새 이름의 검색을 준비한다. 상세·가격·영업시간 요청이면 알려진 대상의 필요한 상세 조회와 새 대상의 검색을 준비한다. 이미 식별됐다는 이유만으로 상세 수집을 시작하지 않는다. 한 대상의 모호함이 다른 대상의 조회를 막지 않는다. 검색 결과 없음과 사용자 입력 부족도 구분한다.

### 5.2 후보 원칙

| 현재 상태 | 후보 |
| --- | --- |
| 실제 호출 가능 | 서로 다른 `tool_call` 최대 3개 + 실제 미지원 부분이 있을 때만 `cannot_answer` |
| 실제 호출 불가능 | 실제로 필요한 `request_for_info` 최대 2개 + 성립하는 `cannot_answer`·`direct` |
| 후보 부족 | 실제 수만 사용. 중복·가짜 인자·불필요한 질문으로 4개를 채우지 않음 |
| 후보 1개 | 실제 Qwen 채점은 하되 ‘단일 유효 후보’로 기록 |
| 후보 0개 | Qwen을 호출하지 않음. 새 작업 없음·준비 실패·미해결 이유를 구분 |

후보는 필드 형식뿐 아니라 현재 요청·대상·방향·권한·취소 여부·선행 작업·이미 완료한 결과까지 확인한다. 현재 요청과 무관한 호출이 인자만 유효하다는 이유로 경쟁하지 않도록 한다. 현재 요청을 우선하고 기존 미완료 작업은 독립적으로 보존한다.

동일 호출은 중복 제거하되 연결된 요청들을 보존한다. 유효 호출이 3개보다 많으면 원문의 대상 순서와 안정적 순서로 제시하고 나머지는 미처리로 남긴다. 실행이 끝난 호출을 다시 제시해 남은 작업이 계속 밀리지 않도록 한다.

`cannot_answer`는 지원하지 않는 행위에만 사용한다. 잡담·대기·일시적 공급자 오류에 사용하지 않는다. 미지원 판정도 요청·부정·취소 범위를 확인한다. ‘대중교통 말고 자동차 경로’는 자동차 경로 요청이다.

질문은 답을 받으면 실제 지원 작업이 진행되는 경우에만 만든다. 항공권 예약을 지원하지 않는데 결제 카드나 출발지를 묻지 않는다. 이미 열린 동일 질문은 재사용하고, 질문의 필드·대상·소유권 계약을 보조 출력부터 화면까지 맞춘다.

`direct`는 관측·확인된 사실과 출처에 근거한다. 검증에서 탈락한 주장을 원문 그대로라는 이유로 확정 사실처럼 답하지 않는다. 실제 값이 캐시에 있으면 그 값을 화면에 제시한다.

| `search_places` | 근거 있는 검색어와 방의 지역 | 검색 결과·후보·결과 없음. 장소 ID 사전 확보는 요구하지 않음 |
| `get_place_details` | 이 방의 관측에서 확인된 대상 참조 | 같은 장소의 확인된 필드, 누락 필드, 출처·매칭 상태. 가격·영업시간 누락은 부분 결과 |
| `get_car_route` | 확인된 출발·도착 참조와 좌표, 현재/여행 시각의 의미가 맞는 출발시각 | 방향이 맞는 거리·시간·통행료와 조회 근거. 메뉴·예산은 준비조건에서 제외 |
| `build_itinerary` | 적어도 계산할 수 있는 방문 구간과 해당 구간의 실제 시간·경로 입력 | 계산 가능한 구간의 초안·충돌·부족 정보. 미확인 시각·경로를 임의 생성하지 않음 |
| `calculate_costs` | 현재 범위의 비용 항목·수량·분담 대상, 확인된 예산 또는 기존 기본 예산 | 확인된 금액·미확인 항목·분담·기지급액. 완전한 일정·경로를 공통 선행조건으로 요구하지 않음 |

### 6.1 장소·영업시간·캐시

상세 조회 매칭은 신뢰할 수 있는 공급자 ID를 우선한다. 도로명·지번 주소를 함께 비교하고 행정구역 표기를 정규화한다. 좌표는 장소 유형과 공급자의 대표점 차이를 고려해 동일 장소 판단에 사용한다. 단순히 반경을 넓히거나 이름만 같으면 통과시키지 않는다. 실제 다지점·복수 후보는 `ambiguous`로 남기고 해당 대상만 보류한다.

‘영업시간 미등록’은 조사 결과의 미확인 상태다. 필요한 관측을 먼저 시도하고, 사용자가 실제로 결정·확인해야 할 내용이 있을 때 질문한다. 영업시간을 묻기 위해 장소 ID를 개인 조건 ID로 오인하는 계약은 고친다. 적절한 기존 질문 타입이 없으면 계약을 함께 보완하며, 임의 대상을 허용해 해결하지 않는다.

‘정기휴무 없음’의 부정을 처리하고, 자정을 넘는 영업시간은 출처의 시간 형식에 맞춰 정규화한다. `00:00–00:00`을 공급자 근거 없이 24시간으로 간주하지 않는다.

캐시는 장소·좌표·조회 조건·사용 날짜에 적합한지 확인한다. 여행 날짜가 바뀌면 영업시간 원문을 새 날짜 범위에 다시 해석한다. 현재 경로와 특정 출발시각 경로를 구분하고, ‘현재’ 경로의 과거 캐시를 무기한 재사용하지 않는다. 공급자 제한과 데이터 성격을 확인해 재사용 기준을 정하며, 모든 데이터에 임의의 동일 TTL을 적용하지 않는다.

경로 캐시는 방향·출발시각·양 끝 좌표를 포함한 적합성을 유지한다. A→B 결과로 B→A를 충족시키지 않으며, `departure_at=null`의 현재 경로를 미래 여행시각의 경로로 표시하지 않는다. 캐시 재사용과 새 외부 관측은 trace와 결과의 시점에서 구분한다.

### 6.2 일정과 비용

방문 생성·후보 준비·계산 준비는 같은 활성/선택 항목 집합을 사용한다. 제외·비활성 항목이 계획 전체를 막지 않도록 한다. 별도의 합의가 없는 한 과반 지지를 조사·초안 계산의 필수 조건으로 추가하지 않는다. 기존 반대·지지에 따른 활성화 정책은 보존한다.

일정은 기존 Visit처럼 시작·종료 시각이 필요한 확정 구간만 시간표에 넣는다. 아직 시각을 계산할 수 없는 활성 방문은 미배치 항목과 이유로 별도 보존하고, 방문이 없어진 것처럼 표시하지 않는다. 이미 정해진 기본 체류시간은 기존 정책에 따라 assumption으로 표시한다. 계산되지 않은 값을 새 기본값으로 채우지 않는다.

비용의 `known_total_krw`, `unknown_line_count`, 미확인 시 `total_krw=null` 의미는 유지한다. 아직 조회하지 않은 필수 구간의 통행료도 미확인 항목으로 포함한다. 관련 비용 자체를 누락해 합계가 완성된 것처럼 표시하지 않는다. 확인된 무료 근거나 명시적으로 포함된 고정비가 있을 때만 해당 중복 비용을 제거한다.

미확인 금액이 있으면 영향을 받는 최종 개인 합계·잔액도 미정으로 유지한다. 기지급액을 뺀 남은 예산과 전체 계획 비용을 뺀 예상 잔액은 기존 의미를 구분한다. 추정액을 표시할 때는 근거와 실제 추정 상태를 연결하고, assumption 설명문만으로 추정 집계가 적용됐다고 가정하지 않는다.

개인 예산 추출은 KRW 정수로 저장 제안하되 본인의 기존 확인 절차를 유지한다. 미확인 개인 조건이 있더라도 가능한 부분 계산은 진행하고, 최종 확정에서는 필요한 본인 확인을 요구한다.

canonical 인자는 현재 범위의 사실로 다시 구성한다. 부분 계산을 허용하더라도 관측된 가격·경로 시간을 후보에서 바꾸는 것은 허용하지 않는다. 경비 카드는 장소 직접 연결이 없는 기존 CostLine에서 설명문을 추측해 장소별 동의 상태를 만들어내지 않는다.

## 7. 요청별 진행·취소·실패

기존 `agent_requests`/`request_states`와 `completed_refs`·`pending_refs`를 재사용한다. 요청 목적 확장, 순수 취소 생성, 요청별 미지원·실패와 결과 연결에 필요한 최소 필드만 보완한다. 저장된 구형 요청은 읽을 수 있어야 한다.

실행 대상으로는 활성 요청만 조회하되 완료·미지원·취소·대체·실패 이력을 다음 저장에서 잃지 않는다. 실행 대상 필터링과 기록 보존을 분리하고, 완료 결과는 이후 새 메시지가 와도 화면에서 확인할 수 있게 한다.

| 상태·사건 | 동작·표시 |
| --- | --- |
| `needs_context` | 기존 대화 확인 중. 사람에게 같은 정보를 다시 요구하지 않음 |
| `needs_input` | 구체적인 질문·대상·응답 권한을 함께 표시 |
| `pending`, 완료·대기 대상 모두 존재 | ‘일부 완료 · 1/2곳’. 새 partial enum 없이 기존 목록에서 계산 가능 |
| `completed` | 실제 저장 결과로 연결. 완료와 사실의 확인 여부는 별도 |
| 미지원 부분 | 그 요청만 안내·종료하고 지원 가능한 다른 요청은 계속 보존 |
| 공급자/계산 실패 | 요청별 오류와 재시도 조건을 표시. 사람의 정보 부족으로 바꾸지 않음 |
| `cancelled` | 연결된 미처리 작업 종료. 다음 재계획에서 자동 재개하지 않음 |
| `superseded` | 정정된 새 요청으로 연결하고 과거 진행·근거는 보존 |

검색·상세 조회를 수행했지만 공급자에 가격이 없으면 ‘조회 완료 · 가격 미확인’으로 표시할 수 있다. 가격을 확인했다고 표시하거나 같은 누락을 해결하려고 무조건 재조회하지 않는다. 사용자에게 답변이나 결과가 제시되지 않은 내부 처리만으로 요청 완료를 선언하지 않는다.

`direct`·`cannot_answer` 선택은 해당 요청의 응답을 완료한다. 다른 미완료 요청까지 전체 종료하지 않는다. ‘두 곳 상세 보여주고 입장권도 예약해줘’는 조회 진행과 예약 미지원 안내를 모두 보존한다.

한 도구의 오류는 같은 요청의 의존 작업만 막는다. 독립적인 유효 작업은 다음 Qwen 판단 대상이 될 수 있다. 같은 상태·같은 실패 호출을 새 잡담마다 반복하지 않으며, 일시 오류는 제한된 재시도, 입력·매칭 문제는 새 정보나 명시적 재시도에 따라 재개한다. 자동 회차 한도가 끝나도 요청을 삭제하지 않는다.

메시지 처리 위치는 추출 확인과 요청 보존이 끝난 뒤 갱신한다. 후보 생성·채점·실행·표시 실패가 있었다고 아직 미완료인 요청이 사라지지 않도록 저장과 재개를 검증한다.

## 8. Qwen 적용과 한계 검증

### 8.1 보존할 것

제공 베이스 `Qwen2.5-1.5B-Instruct`, LoRA, 토크나이저, `submission.judge.judge_prompt`·`judge_scores`, 후보별 `logit(yes)-logit(no)`와 argmax를 유지한다. 원본 제출 패키지의 4지선다 계약을 서비스 변경으로 개편하지 않는다.

도구명은 입력으로 제공되는 문자열이며 고정된 도구 클래스 목록으로 제한되지 않는다. 그러나 새 도구의 적절한 선택·인자 관계·실행 순서를 정확하게 평가한다는 보장은 아니다. 현재 어댑터의 정확한 학습 데이터·언어 구성은 파일만으로 확인하지 못했다.

베이스 모델은 [공식 설명](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct)상 한국어를 지원한다. [When2Call](https://github.com/NVIDIA/When2Call)은 네 가지 응답 유형 판단을 다루며, 우리 서비스의 여러 유효 호출 중 다음 행동 선택이나 이미 확인된 사실의 직접 응답과는 과제 차이가 있다. 이를 정확한 어댑터 학습 원인의 증명으로 사용하지 않는다.

### 8.2 입력 보완

서비스 입력에는 현재 요청, 확인된 사실, 관련 원문, ID→장소 이름 대응, 미해결 내용, 정확한 도구 정의를 짧게 제공한다. 관측값이 요청과 함께 주어진 사실임을 분명히 한다. 도구 스키마는 실제 계약에서 필수 인자·타입·의미를 공유하며, 계산 도구의 중첩 입력도 의미를 확인할 수 있게 설명한다.

후보의 실제 호출 JSON과 실행 인자는 동일하게 유지한다. 설명을 덧붙이더라도 호출을 다른 인자로 바꿔 채점하지 않는다. 원시 경로 좌표 배열·무관한 기록·중복 관측·보조 모델 추천 순위는 입력에서 제외한다. 길이 초과 시 필요한 근거를 조용히 잘라 채점하지 않는다.

읽기 쉬운 입력 묶음이 기존 JSON 입력보다 낫다는 것은 검증할 가설이다. 전체 영어 번역을 기본으로 채택하지 않는다. 같은 사실·후보를 고정해 직렬화 방식과 요청 언어를 각각 비교한 뒤 선택한다.

### 8.3 이미 관측한 진단과 해석 범위

2026-11-19 제공 모델·LoRA와 기존 서비스 scorer로 6개 합성 상황을 한국어·영어 각각 평가했다. 각 입력은 경쟁 후보 4개였고, 장소명·참조는 동일하게 유지했다. DB·보조 API·실제 도구를 호출한 운영 테스트가 아니다.

| 상황 | 관측 |
| --- | --- |
| 명확한 검색, 상세 대상 선택 | 한국어·영어 모두 기대 선택 |
| 대상 불명확 | 한국어는 질문, 영어는 미지원 선택 |
| 항공권 예약 + 무관한 공원 검색 후보 | 두 언어 모두 무관한 검색 선택 |
| 정방향/역방향 경로 경쟁 | 두 언어 모두 역방향 선택 |
| 확인된 주소 직접 응답 | 두 언어 모두 답변 불가 선택 |

진단에는 의도적으로 부적절한 후보가 포함됐다. 현재 후보 생성기가 그 후보를 실제로 만든다는 증거가 아니며, 이를 서비스 전체 정확도로 환산하지 않는다. 영어 응답 문구도 함께 바뀌어 순수 언어 효과를 분리한 실험은 아니다. 단일 후보·동등하게 유효한 두 검색의 성공 역시 오선택 판별 정확도의 증거로 사용하지 않는다.

로컬 재현 자료는 `.planning/qwen-language-tool-audit/probe.py`와 `results.json`이다. 이 파일들은 Git 제외 자료이므로 공유된 문서를 이해하는 데 필수로 요구하지 않는다. 위 표가 관측 요약이다. 입력 보완 후에도 실패하면 모델의 잔여 한계로 명시하고, 점수 보정·임의 후보 대체로 성공처럼 처리하지 않는다.

4명 중 2명 지지는 `mentioned`지만 ‘일부 지지 2/4’로 표현한다. 미응답·반대·철회는 구분한다. 지도 클릭·조회 성공·방문 제안만으로 찬성이나 확정을 만들지 않는다. 개인 필수 조건은 다수결로 완화하지 않는다.

### 9.2 정보 확인과 결과

`Evidence.status`·`match_status`·출처·조회 시각, 미확인 값 `null`, 기존 assumptions를 활용한다. ‘API에서 관측됨’은 현장 정확성 보증이 아니다. 확정된 여행안에도 허용된 비필수 가정과 정보의 시점은 남는다. 필수 입력·차단 충돌이 남은 계획은 확정하지 않는다.

| 화면 | 표시 |
| --- | --- |
| 지도 | 방문 번호 + 동의 상태 텍스트/테두리 + 범례. 좌표 미확인은 목록에 보관. 실제 관측 경로와 미조회 구간을 구분 |
| 장소 상세 | 공유 항목의 동의·지지·반대, 계획 포함 여부, 가격·영업시간 확인 상태·출처·시각 |
| 일정 | 초안/검토/확정 버전, 방문별 동의·충돌, 계산된 구간과 미배치 항목·이유 |
| 경로 | 어느 여행안의 경로인지와 조회 조건. 구간마다 사람의 표를 새로 만들지 않음 |
| 비용 | 여행안 버전·초안/확정 상태, 확인 금액·미확인 항목·기지급액. 장소별 표를 설명문에서 추측하지 않음 |
| 기존 작업 영역 | 원문에 연결된 요청별 완료/대기/질문/오류/취소와 결과 링크 |

색만으로 상태를 전달하지 않고 텍스트·체크·충돌 `!`를 함께 쓴다. 기존 지도 경로선 색을 동의 상태로 오인하지 않게 한다. 합의 갱신 시 지도·일정·상세·비용의 렌더 조건도 갱신한다.

현재/검토/확정 여행안을 구분하고 항목 ID와 버전을 맞춰 표시한다. 현재 표를 과거 snapshot의 당시 표처럼 보여주지 않으며, 지지 수를 여행안 의미 해시에 새로 넣지 않는다. 기존 review snapshot 고정과 확정 대상 검사를 유지한다.

## 10. 실행·반영·최종 확정

후보 준비·채점·trace·실행에는 같은 호출과 관련 기반 버전을 사용한다. 실행 직전, 특히 trace 전송을 기다린 뒤에는 요청 취소·대상 정정·항목 버전·참조 적합성을 다시 확인한다. 관련 변경이면 호출을 조용히 수정하거나 차순위로 대체하지 않고 다시 준비·판단한다.

신선도 검사는 버전 카운터만 비교하지 않는다. 현재 코드가 확인하는 메시지·질문·구성·검토/확정 상태·미처리 요청·관측의 판단 snapshot과 등록된 run의 식별·미반영 여부도 유지한다. 오래된 결과는 계획뿐 아니라 응답·질문·요청 완료 상태도 발행하지 못하게 한다.

실행 권한 확인과 호출 시작은 기존 방 실행 직렬화 경계에서 순서가 정해지도록 한다. 이미 외부 조회가 시작된 뒤 들어온 취소가 네트워크 요청까지 소급 취소된다고 보장하지 않는다. 대신 결과 반영 시 다시 상태를 검사해 오래된 결과가 현재 요청을 완료시키거나 여행안을 바꾸지 못하게 한다. 재사용 가능한 관측 보존 여부와 현재 계획 적용은 구분한다.

최종 확정은 기존 정책을 유지한다: 같은 확인 대상의 전원 확인, `validation=ready`, 차단 충돌 없음, 본인 확인이 필요한 필수 조건 없음. 전체 활성 선택 항목·필수 경로·최종 비용 완성 검사를 생략하지 않는다. 부분 결과의 존재나 도구 실행 성공은 `ready`를 뜻하지 않는다.

기존 DB·방·메시지·확정안을 보존하고 초기화하지 않는다. 확장 필드가 없는 저장 기록은 기본값과 호환 읽기로 처리한다. 제품 계약 변경은 FE·BE·AI에서 함께 반영하며, trace를 제품 데이터 전달 통로로 사용하지 않는다.

## 11. 검증 기준

### 11.1 우선 회귀 시나리오

| 입력·상황 | 통과 기준 |
| --- | --- |
| ‘오동도 가자. 내 예산은 15만원’ | 장소·본인 예산·명시적 지지 모두 반영하거나 각각 미해결 표시. 일부 성공으로 전체 누락을 숨기지 않음 |
| ‘한강공원 좋아하지 않아’ / 최신 제외 | 잘린 인용을 찬성으로 저장하지 않고 최신 정정 우선 |
| 2차 보조가 누락 정보를 출력하지 않음 | 해결 근거 없는 요청·질문 유지 |
| ‘대중교통 말고 자동차 경로’ | 미지원 대중교통 요청으로 잘못 분류하지 않음 |
| 항공권 예약 / 장소 조회와 예약의 복합 요청 | 불필요한 예약 질문 없음. 지원 조회와 미지원 안내 각각 처리 |
| ‘아까 고른 두 곳 상세 보여줘’, 대상 불명확 | 기록으로 해소하거나 실제 답할 수 있는 대상 질문 표시. 질문 없는 입력 요구 없음 |
| 알려진 장소 + 새 장소 ‘찾아줘’ | 단순 위치는 기존 검색 결과 재사용 + 새 대상 검색. 상세 요청은 필요한 상세 조회 + 새 대상 검색. 전체 요청을 비우지 않음 |
| 미완료 조회 후 ‘아까 조회 취소해’ | 취소 범위 기록, 후속 실행에서 재개하지 않음 |
| ‘아까 영업시간 다시 보여줘’ | 적합한 캐시의 실제 값·출처 표시. 완료 표시만 하지 않음 |
| 예산과 무관한 귀가시간 부정 | 예산 정규화·본인 확인 유지, 거짓 귀가 조건 없음 |
| 제외 장소 하나 / 경로 일부만 확보 | 제외 장소가 전체 계산을 막지 않음. 가능한 초안·미배치 이유 표시 |
| 부분 비용 / 통행료 미조회 | 알려진 금액 유지, 미확인 비용 포함, 최종 합계 `null` |
| 주소 표기 차이 / 실제 다른 지점 | 같은 장소의 표기 차이는 정규화, 다른 지점은 거절·모호성 유지 |
| 영업시간 미등록·휴무 없음·익일 종료 | 부분 결과·부정·자정 경계를 올바르게 표시 |
| trace 대기 중 정정 / 외부 호출 중 취소 | 시작 전 변경은 오래된 호출 차단, 시작 후 변경은 오래된 반영 차단 |
| 단일 후보·0개·채점 실패·회차 한도 | 가짜 후보·임의 대체 없음. 미완료 요청과 재개 상태 보존 |

이 표에는 사용자가 제공한 10개 검토 항목을 포함한다. 코드에서 의심한 공백과 실제 재현한 결함을 구분하고, 이미 방어된 경로도 회귀로 유지한다.

### 11.2 모델·통합 검증

1. 외부 호출 없는 회귀로 정규화·질문 계약·부분 결과·취소·병합·버전 경쟁을 먼저 확인한다.
2. 실제 Qwen에서 네 응답 유형 경쟁과 여러 도구 호출 경쟁을 별도로 평가한다. 후보 하나의 argmax 성공을 선택 정확도로 보고하지 않는다.
3. 입력 방식 비교는 사실·후보를 고정하고 직렬화만 바꾼다. 언어 비교는 요청 언어와 응답 언어를 따로 바꾼다. 방향·참조 변경에 선택이 따라가는지도 확인한다.
4. 실제 생성된 후보로 수행한 서비스 검증과 부적절한 후보를 의도적으로 넣은 모델 진단을 분리한다. 복수 유효 정답은 허용 가능한 선택 집합으로 판정한다.
5. 기존 DB를 보존한 별도 테스트방에서 실제 보조 모델→후보→Qwen 점수·선택→선택된 동일 호출→공급자/계산→DB 반영→화면 표시·미처리 상태를 연결해 확인한다.

기존 trace에 요청·회차·실제 후보 수·내용·근거·점수·선택·실행 인자·캐시/실제 호출·결과·적용 여부·소요시간을 연결한다. 비밀값과 모델의 비공개 추론은 기록하지 않는다. 상태 반영은 trace가 아닌 제품 저장 결과로 검증한다.

완료 기준은 대표 시나리오에서 근거 없는 조건·불필요한 질문·무관한 호출 없이 요청별 결과가 표시되고, 미해결 내용이 보존되며, 최종 확정 경계가 유지되는 것이다. 실제 모델의 잔여 오선택은 성공으로 덮지 않는다. 지연은 보조·Qwen·도구별 시간과 전체 처리 시간, 문맥 확대·실제 후보 수를 함께 보고해 품질 저하와 구분한다.
