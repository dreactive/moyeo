# 공동 여행 Agent MVP 설계

- 기준일: 2026-11-18, Asia/Seoul.
- 상태: 사용자 답변을 반영한 구현 전 설계. 코드·모델 성능·외부 API 성공을 보고하는 문서가 아니다.
- 우선순위: **Agent의 실제 판단 → 실제 도구 조회 → 계획 갱신 → 사용자 선택·전원 확인**이 작동하는 것.
- 최신 구현 기준: 이 문서와 [API 계약](../../contracts/travel-api.md). 기존 [서비스 기획 v1.0](../../travel-agent-service-plan.md)은 서비스 의도와 평가 배경으로 보존한다. 충돌하는 세부 범위는 2026-11-18 사용자 답변을 반영한 이 문서를 따른다.
- 읽는 순서: [3세션 총괄](../plans/2026-11-18-three-session-plan.md) → 이 설계 → API 계약 v0.2 → [공급자 조사](../../providers/place-data.md) → [FE](../plans/2026-11-18-frontend.md) / [BE](../plans/2026-11-18-backend.md) / [AI](../plans/2026-11-18-ai.md) 계획 → [검증표](../../testing/mvp-checklist.md).

## 1. 확정 범위와 설계자가 정한 값

| 구분 | 내용 |
|---|---|
| 사용자 확정 | 국내 한 도시, 대표 데모 여수·4명·1박 2일. 자동차만 지원 |
| 사용자 확정 | 숙소·출발/귀가 지점과 숙박·장거리 교통비는 입력. 관광지·식당·카페·도시 내 일정/동선은 Agent가 조사 |
| 사용자 확정 | 전체 여행 1인당 예산. 기지출 포함. 공용 비용은 균등 분담 |
| 사용자 확정 | 가격·영업시간도 실제 API 조회. Naver 연동이 어렵다면 무료 API로 전환 |
| 사용자 확정 | 항목별 빨강/노랑 표시. 여행안 전체에 모든 참가자가 ‘확인’을 누르면 포함 항목 초록 확정. 충돌에는 느낌표 |
| 사용자 확정 | 모델 교체 가능. 현재 PC에서 시작. 가상 대화로 먼저 검증 |
| 사용자 확정 | frontend/, backend/, ai/로 분리. 화면은 기능 확인용 HTML. 복잡한 Backend 예외/오류 체계는 최소화 |
| 설계 기본값 | 노랑 기준은 현재 참가자 **과반수 = floor(N/2)+1**. 4명 중 3명, 3명 중 2명 |
| 설계 기본값 | Agent는 하나, 로컬 Qwen은 생성/판단 두 모드, 모델 추론 큐는 하나 |
| 설계 기본값 | 최근 메시지 20개 + 구조화된 방 상태 + 현재 작업의 도구 결과로 모델 입력 구성 |
| 설계 기본값 | 외부 장소 정보는 공급자 어댑터 뒤에 감춤. Apify는 우선 HTTP로 검증하고 MCP는 후속 선택지 |

예약·결제, 도보/대중교통, 숙소 예약 가능 객실 탐색, 도시 간 교통 선택, 목적지/날짜 협상, 부분 동행, 별도 모바일 UI는 이번 범위에서 제외한다. 모델 재학습과 SABench 전체 어댑터도 MVP 선행 작업으로 두지 않는다.

## 2. 접근법과 선택 이유

| 접근법 | 장점 | 부담 / 선택 |
|---|---|---|
| judge 어댑터 하나로 생성·판단 모두 처리 | 호출 경로가 하나 | 현재 어댑터의 생성 품질 근거가 없어 첫 구현에서 제외 |
| **같은 Qwen 베이스에서 생성/판단 모드 전환** | 기존 submission을 실제 판단에 재사용, 추가 모델 없이 시작 | 한국어 추출 품질을 먼저 측정. **선택한 기본안** |
| 큰 보조 모델 + submission 판단 | 생성 품질 보완 가능 | 추가 실행 자원·모델 준비가 필요해 후속 대안 |

Agent 실행기는 프레임워크의 복잡한 그래프 대신 **명시적 상태 + 도구 레지스트리 + 제한된 반복 루프**로 작성한다. 참고 저장소의 단일 Agent·도구 목록·call ID 기반 trace 원칙을 취한다. HTTP 공급자 호출을 먼저 만들면 MCP 연결은 같은 도구 계약 뒤에서 나중에 바꿀 수 있다.

이 선택은 성능 검증 결과가 아니다. 베이스 생성, judge 행동 선택, 실제 API의 데이터 범위는 개발 첫 단계에서 검증한다.

## 3. 디렉터리와 책임

아래는 구현 때 만들 경로다. 현재 문서 작업에서 제품 폴더나 실행 코드를 생성하지 않는다.

```text
frontend/
  index.html                 # 가입/로그인/방 입장 및 여행 작업 화면
  dev.html                   # 개발자 trace 확인 화면
  styles.css                 # 배치와 빨강/노랑/초록·충돌 표시
  src/{api,events,state,room,map,items,plan,dev-trace}.js
  fixtures/room-snapshot.json # 계약에 맞는 개발용 데이터, fixture 표시
backend/
  app.py                     # FastAPI 구성, 같은 origin에서 HTML 제공
  config.py                  # 서버·외부 API 설정
  db.py                      # SQLite 연결 및 작은 초기 스키마
  domain.py                  # 저장 상태와 색상/동의 계산
  schemas.py                 # HTTP DTO
  auth.py                    # 단순 계정·세션
  ports.py                   # AI 구현 import가 필요 없는 JSON AgentPort
  adapters/{fixture_agent,local_ai}.py # 독립 테스트 대역 / 통합 시 지연 연결
  requirements.txt, .env.example, pytest.ini # S2 독립 환경
  routes/{auth,rooms,messages,plans,places,dev}.py
  services/{rooms,consensus,planning,agent_jobs,events}.py
  tests/                     # 도메인·API 통합 검증
ai/
  contracts.py               # AgentInput/AgentResult/ModelBackend/ToolExecutor 경계
  runner.py                  # 단일 Agent 반복 실행
  runtime.py                 # create_runtime + run/execute_tool/aclose 공개 경계
  requirements.txt, .env.example, pytest.ini # S3 독립 환경
  context.py                 # 최근 대화와 구조화 기억
  extraction.py              # 조건·정정·대상별 동의 발언 추출
  candidates.py              # 현재 목표와 상태로 다음 행동 후보 구성
  prompts/                   # 생성·판단 입력 템플릿
  models/{local_qwen,fake}.py # Qwen 어댑터 전환 / 계약 검증용 모델
  tools/{registry,places,routes,itinerary,costs}.py
  providers/{apify,jeonnam,kakao,tourism}.py
  trace.py                   # 결정·도구 호출·결과 이벤트
  eval/{cases.jsonl,replay.py}
  tests/
docs/                        # 공통 설계·API·공급자·계획·검증표
  contracts/examples/        # 세 세션이 읽기만 하는 공통 JSON 예제
  verification/              # frontend/backend/ai별 기록과 S2 통합 기록
submission/                  # 기존 대회 제출물. 그대로 보존
data/                        # 검증 대화·허용된 근거/리플레이, 외부 원본 무분별 적재 금지

```

ai는 FastAPI·SQLite를 import하지 않고 Backend도 독립 개발 단계에서 ai 타입·모델을 import하지 않는다. Backend가 자기 AgentPort에 AgentInput JSON을 전달하고 AgentResult JSON의 변경 제안만 적용한다. 실제 연결은 Backend 어댑터에서 create_runtime을 지연 import한다. FE는 HTTP/SSE 계약만 사용한다. 통신 계약의 원본은 Markdown과 동결 JSON 예제이며 구현 뒤 FastAPI OpenAPI와 맞춘다.

S1은 frontend, S2는 backend, S3는 ai와 각자 검증 기록만 수정한다. Backend/AI는 별도 의존성·환경을 두며 공용 루트 파일/체크리스트는 S2 통합 담당자가 한 번 취합한다. 구체 소유권과 작업 공간 규칙은 3세션 총괄을 따른다.

## 4. 최소 사용자 흐름

1. 계정으로 로그인해 여행방 생성 또는 코드 입장.
2. 여수·날짜·예산·출발/귀가 지점·숙소·고정비 입력.
3. 사람들은 왼쪽에서 대화. Agent의 조건·질문·조사·계획은 오른쪽에만 표시.
4. 장소 언급은 공동 결정 항목이 되어 빨강 표시. 개인 조건은 발언자·근거·필수/선호를 붙여 추출하고 본인이 확인.
5. Agent가 장소·가격/시간·자동차 경로를 조회하고 일정·경비 초안 생성.
6. 명시적 지지 발언이 과반이면 해당 항목 노랑. 충돌에는 `!`와 설명·선택지를 표시.
7. 사용자 선택을 반영해 관련 장소·동선·경비를 같은 새 버전으로 갱신.
8. 참가자들이 같은 여행안 전체에 ‘확인’. 전원 확인과 필수 조건 충족이 확인되면 초록 확정.
9. 조건/일정/근거를 실질적으로 바꾸면 새 안에서 다시 확인. 이전 확정안은 이력으로 보존.

선택 장소와 지도 확대는 개인 화면 상태다. 다른 사용자의 열람을 바꾸거나 여행안 버전을 생성하지 않는다.

## 5. 색상·대화 지지·전원 확인

### 5.1 항목별 표시

| 상태 | 표시 | 계산 |
|---|---|---|
| mentioned | 빨강 + ‘언급됨’ | 공동 항목이 있으나 현재 item_version의 명시 지지가 과반 미만 |
| supported | 노랑 + ‘다수 지지’ | 서로 다른 참가자 지지가 floor(N/2)+1 이상. **확정 아님** |
| confirmed | 초록 + ‘확정’ | 전원 확인된 여행안의 해당 스냅샷에 포함됨 |
| conflict | `!` + 설명 | 색상과 독립된 표식. 색상으로 충돌을 덮지 않음 |

단순 언급 ‘A식당?’은 지지로 세지 않는다. 본인의 ‘A식당 가자’, ‘A식당 좋아’는 자신 1명의 지지다. ‘다들 찬성했어’가 다른 사람의 지지를 만들지는 않는다. 같은 사람의 반복 찬성은 한 번만 센다. 명시적 철회/반대는 그 사람의 지지를 제거한다. 애매한 ‘좋아’의 대상이 여러 개면 지지를 생성하지 않고 확인 필요로 남긴다.

채팅 지지는 표시·추천에만 사용한다. 최종 confirmation은 로그인한 본인의 ‘확인’ 클릭으로만 만든다. 개인 필수 조건은 다수결로 완화하지 않는다.

### 5.2 버전과 확인

- 확인 대상은 `plan_revision + participant_version + constraint_version + evidence_version + content_hash`다.
- 첫 ‘확인’ 클릭이 현재 초안을 불변 동의 대상으로 올리고 그 사람의 찬성을 기록한다.
- 이 동안 Agent가 새 초안을 만들 수 있지만, 검토 중 안을 바꾸지는 않는다. 새 안을 채택하려면 사용자가 ‘새 안으로 전환’을 누른다. 이전 표는 재사용하지 않는다.
- 4명 중 3명 확인은 미확정. 마지막 1명이 같은 대상을 확인하고 필수 조건/충돌 검증을 통과하면 확정.
- 항목을 실질적으로 수정하면 item_version을 올리고 그 항목의 대화 지지는 다시 모은다. 다른 항목의 대화 지지는 보존할 수 있으나 새 여행안 전체의 확인 표는 새로 받는다.
- 새 제안과 기존 초록 확정안은 별도로 표시한다. 새 조건에 충돌이 생겼다고 과거 확정 스냅샷을 몰래 고치지 않는다.

## 6. 충돌을 사람이 선택하도록 만드는 방식

충돌 종류는 `time`, `budget`, `opening_hours`, `personal_constraint`, `preference`다. 각 충돌은 영향 항목·근거·설명·선택 가능한 대안을 가진다.

- ‘16시까지 역 도착’과 현재 동선이 충돌하면 ‘장소 하나 제외’ / ‘순서 변경’을 조사해 제안한다.
- 시간·영업시간·예산 충돌은 실제 도구 값과 코드 계산으로 확인한다.
- 필수 조건을 모두 만족하는 안들 사이의 선호 차이는 설명과 비교를 제공하고 사용자가 선택한다. Agent가 다수 의견을 이유로 소수의 필수 조건을 삭제하지 않는다.
- 선택은 새 초안을 만드는 동작이다. 선택만으로 초록 확정하거나 확인 표를 생성하지 않는다.
- 개인 필수 조건 완화가 필요한 선택은 그 소유자의 조건 수정·확인을 통해서만 반영한다.
- unresolved blocking conflict 또는 필수 검증 미확인이 있으면 최종 확정은 대기한다. 선택 가능한 선호 차이와 실행 불가능한 충돌을 구분해 `blocking`에 담는다.

## 7. Agent 구조와 완료 조건

### 7.1 실행 계기

새 메시지는 바로 저장·전달한다. 최근 메시지 묶음의 추출 결과에서 새 조건·정정·공동 후보·명시 지지 변화가 있을 때 관련 작업만 시작한다. 잡담이나 반복 발언은 장소/가격/경로 재조회로 연결하지 않는다. 사용자가 ‘다시 계획’ 또는 충돌 대안을 선택해도 실행한다.

### 7.2 한 작업의 흐름

1. Backend가 현재 상태와 version 묶음을 `AgentInput`으로 전달.
2. 베이스 Qwen 생성 모드가 조건·정정·지지 대상을 근거 message ID와 함께 구조화.
3. 현재 작업 목표와 이미 있는 결과를 비교해 조회/추가 확인/처리 불가 후보 구성.
4. judge 모드가 실제 다음 행동을 선택. 코드가 등록 도구와 필수 인자를 확인한 뒤 실행.
5. 도구 결과를 관측에 넣고 다시 판단. 여러 장소 상세·자동차 구간·일정·경비 조회를 끝낼 수 있도록 최대 20회 행동 선택을 초기 기본값으로 둔다. 필요한 결과가 갖춰지면 즉시 종료하며 20회를 채우는 고정 흐름은 아니다. 실제 호출 수와 속도를 측정해 조정한다.
6. 일정 조립·동선·비용 계산은 코드로 수행. 필요한 필드가 없으면 입력 요청/미확인 결과를 반환.
7. `AgentResult`에 변경 제안·질문·충돌·도구 근거를 담아 Backend에 전달.
8. Backend가 기반 버전을 확인한 후 여행안·지도·경비를 한 버전으로 반영하고 SSE 알림.

잡담 대기, 이미 확보한 결과 표시, 코드가 확인한 작업 종료는 실행기의 상태 판단으로 처리한다. When2Call식 judge에는 조회/추가 확인/미지원 선택이 필요한 상황을 넘긴다. 서비스의 정상 direct/wait/finish를 원래 평가의 직접 답변 오답과 같은 것으로 취급하지 않는다.

작업 완료는 ‘모델이 완료라고 말함’이 아니라, 요청된 조회 결과와 계산된 계획 또는 명시적 입력 요청/미지원 결과가 저장되어 오른쪽에 나타난 상태다. 근거 없는 직접 답변이나 새 가격·영업시간 생성을 완료로 세지 않는다.

### 7.3 교체 가능한 모델

AI 실행기 내부는 ModelBackend.generate_json(request)와 score_candidates(context,candidates)를 사용한다. local_qwen은 한 베이스를 로딩하고 생성 시 judge LoRA를 끄며 판단 시 켠다. 모델 인스턴스와 직렬화 장치는 AI가 소유한다. Backend는 방 작업 큐와 JSON AgentPort만 관리하므로 모델 구현이나 모델 패키지 설치를 기다리지 않는다.

대회 `TeamPredictor.predict()`의 후보4개 계약과 패키지는 보존한다. 서비스는 하위 판단 기능을 별도 래퍼에서 사용하고 후보를 억지로 4개로 채우지 않는다. 기존 ‘실패하면 choice0’ 경로를 실행 권한으로 재사용하지 않는다. 점수는 비교 점수이며 확률로 표시하지 않는다.

fake 모델은 계약·상태 흐름 검증 전용이다. fake 통과와 실제 Qwen 검증 통과를 구분한다.

## 8. 장소·가격·영업시간과 비용

- 지도와 자동차 경로는 Kakao 계열 API 사용. 메뉴·시간은 [공급자 문서](../../providers/place-data.md)의 공통 계약으로 정규화.
- Apify 입력/출력 스키마를 실제로 연결해 검증하고, 연결이 어렵거나 필요한 커버리지가 나오지 않으면 사용자 지시에 따라 무료 전남 API 등을 선택한다.
- 매장명만으로 메뉴를 연결하지 않는다. 공급자 매장 ID, 주소·좌표·전화 중 확인 가능한 근거로 동일 매장을 판정한다. 애매하면 선택 요청.
- API를 지금 호출했다는 것과 가격/시간이 오늘 갱신됐다는 것은 다르다. 조회 시각과 공급자 기준일은 별도 보관·표시.
- ‘시가’, 공란, 미등록은 0원이 아니다. 조회가격, 명시적 추정, 사용자 입력, 미확인을 구분한다. 이번 가격/시간 조회 기능의 완료 판정에는 **실제 API 값**이 필요하다.
- 메뉴 가격은 자동으로 1인 식비가 되지 않는다. 선택 메뉴·수량·공유 여부를 비용 가정으로 남긴다. 기본 제안은 ‘1인 메뉴 1개’지만 실제 제공 단위가 불명확하면 사용자 선택을 받는다.
- 숙박·왕복 교통·기지출은 사용자 입력. 도시 내 자동차 비용의 유류·주차비를 API가 주지 않으면 포함 여부·입력 필요를 표시한다. 통행료를 전체 차량 비용으로 오인하지 않는다.
- 전체/1인 총액, 기지출, 앞으로 쓸 수 있는 예산, 미확인 항목 수를 보여준다. 미확인 비용이 있으면 완전한 예산 검증을 했다고 표시하지 않는다.
- ‘앞으로 쓸 수 있는 예산’은 예산−기지출이고, ‘계획 반영 후 여유’는 예산−전체 계획액이다. 두 계산을 별도 표시한다. 활동 구간 기본09:00-18:00과 관광/식사60분·카페40분은 API 사실이 아닌 변경 가능한 일정 가정이다.

## 9. 통신·저장·개발자 trace

FastAPI와 SQLite로 단일 프로세스부터 시작한다. FE는 같은 origin의 HTML/ES modules다. 채팅 송신은 POST, 서버 변경 수신은 방 SSE 한 연결. FE는 알림에 따라 필요한 데이터 또는 방 스냅샷을 다시 받는다. React와 WebSocket은 필수가 아니다.

trace는 `decision`, `tool_call`, `tool_result`, `state_applied` 이벤트를 run_id/step/call_id로 연결한다. 판단 후보·점수·실행 도구·정규화 결과·변경 요약·소요 시간을 보여주고 비공개 추론 텍스트는 요구하지 않는다. 비밀 키는 기록하지 않는다. 공급자 원문 보관 범위는 해당 공급자 조건에 맞추고, 실시간 메모리 결과와 영구 로그를 구분한다.

사용자 SSE에는 trace를 보내지 않는다. 개발자 전용 API는 `X-Dev-Token` 하나로 접근을 제한한다. 복잡한 관리자 체계나 관측 플랫폼은 만들지 않는다.

## 10. 세 세션 병렬 개발과 검증

1. S1은 F1-F5를 브라우저 fixture로, S2는 B1-B4를 FixtureAgentPort로, S3는 A0-A5를 fake/fixture JSON 재생으로 즉시 시작한다.
2. 실제 공급자·Qwen 확인은 S3 A1에서 진행하되 S1/S2 및 AI의 나머지 오프라인 개발을 선행 차단하지 않는다.
3. G1은 각 세션 독립 완료다. 다른 폴더가 없어도 자기 테스트가 실행되어야 한다.
4. G2는 BE↔AI fake runtime 연결, G3는 FE↔BE fixture Agent 연결이다. 두 통합은 서로 선행 조건이 아니며 GPU·실 API 없이 가능하다.
5. G4는 실제 Qwen·실 API·4인 전체 흐름이다. S2가 [공통 체크리스트](../../testing/mvp-checklist.md)와 세션별 증거를 취합한다.
6. 독립 개발의 완료와 실제 기능 통합 완료를 별도로 보고한다. 세 세션에 같은 DB·Git index·GPU 실행을 공유시키지 않는다.

테스트는 핵심 의미·계산·상태와 실제 연결에 집중한다. 복잡한 오류 분류·재시도 프레임워크·마이크로서비스·대규모 배포는 이번 계획에 넣지 않는다. 로컬 개인 구현·커밋 규칙은 실제 구현을 요청받은 뒤 적용하며 문서 작성만으로 Git 초기화·커밋·push를 시작하지 않는다.

## 11. 남은 확인의 성격

사용자 의도가 필요한 미결정 사항은 현재 없다. 남은 것은 **API 키 준비, 실제 API의 여수 커버리지·최신성, 베이스 가중치 경로, 생성 품질·속도** 같은 실행 확인이다. 이 사실을 확인하지 않고 기능 성공이나 계획의 현실성을 미리 주장하지 않는다. 무료 후보에 여수 가격·시간이 없으면 지원 범위를 몰래 부산으로 바꾸거나 고정 값을 실제 API처럼 내보내지 않는다.
