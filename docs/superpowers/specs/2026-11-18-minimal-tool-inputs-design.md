# 보조 모델 문맥 보완과 Qwen 최종 행동 선택 설계

- 수정일: 2026-11-18
- 상태: 사용자 승인 후 `codex/qwen-judge-tool-execution`에서 구현·검증한다.
- 제공 모델·LoRA 파일과 기존 DB·서버는 보존한다. 구현과 테스트를 마친 뒤 커밋하며 push·PR은 범위에 넣지 않는다.
- 이 문서는 이전 v2를 대체한다. 개발자 scope·쿠키·만료 관리·별도 진단 API 구축은 이번 구현 범위에 넣지 않는다. 기존 개발자 기능의 삭제를 지시하는 것은 아니다.

## 1. 목표와 역할

보조 모델로 대화를 해석하고 필요한 문맥만 보완한 뒤, 제공된 Qwen judge가 실제 서비스 행동을 최종 선택한다. 모든 채팅은 보존하되 도구 호출과 무관한 입력마다 전체 대화나 Qwen을 반복 호출하지 않는다.

| 구성 요소 | 책임 |
| --- | --- |
| 외부 보조 모델 | 장소·조건·대상별 찬반·정정·누락 정보를 원문 근거와 함께 구조화 |
| 서비스 코드 | 관련 문맥 조회, 인자 완성·검증, 응답 후보 구성, 상태 반영 |
| 제공된 Qwen + LoRA judge | 준비된 후보를 기존 방식으로 채점하여 최종 선택 |
| 기존 도구 실행기 | 선택된 호출을 검증하고 기존 공급자·캐시·계산 로직으로 실행 |

LangChain은 외부 보조 모델의 구조화 호출과 공통 도구 스키마 관리에만 적용한다. 도구 설명·인자 스키마는 하나의 기준에서 공유하고 기존 업무 검증을 재사용한다. 보조 모델에 서비스 도구의 직접 실행 권한을 주거나 별도의 자동 Agent 실행 루프를 만들지 않는다.

## 2. 처리 흐름

```text
채팅 원문 저장
→ 현재 발화와 최소 방 상태 확인
→ 명백한 단독 잡담이면 새 작업 없이 종료
→ 1차 보조: 의미·근거·부족한 정보 구조화
→ 요청에 맞는 유효한 도구 호출을 만들 수 있는가?
   ├ 가능 → 유효 분기 후보 구성
   └ 불가능
      → 이전 기록에서 보완할 정보가 있는가?
         ├ 있음 → 관련 기록 조회 + 2차 보조 → 호출 준비 상태 재확인
         └ 없음 → 비유효 분기 후보 구성
→ Qwen judge로 최종 비교
→ 선택된 도구 실행 또는 질문·안내·직접 답변
→ 결과와 요청별 진행 상태 저장
```

1차·2차 보조는 같은 외부 모델을 다른 입력 범위로 사용할 수 있다. 2차는 1차가 받은 사실을 재사용하며 필요한 기록만 추가한다. 2차 보조를 모든 채팅에 병렬 실행하지 않는다.

‘Qwen 1회’는 한 판단 회차에서 문맥을 보완한 뒤 최종 비교를 한 번 한다는 뜻이다. 기존 judge는 후보마다 독립 계산하므로 한 번의 forward라는 뜻은 아니다. 검색 결과가 있어야 상세·경로 후보를 만들 수 있는 연쇄 작업은 새 결과를 반영한 다음 판단 회차로 진행한다.

## 3. 문맥과 근거

| 입력·상태 | 포함할 내용 |
| --- | --- |
| 1차 보조 입력 | 현재 메시지·작성자·메시지 ID, 지역·날짜, 관련 장소·조건·미해결 질문 등 최소 상태 |
| 2차 보조 입력 | 해석에 필요한 이전 발화·정정·질문 답변·관련 관측만 추가 |
| Qwen 판단 입력 | 현재 요청, 판단에 필요한 사실·원문 근거·누락 정보, 도구 정의, 응답 후보 |
| 서버 실행 context | 검증·계산에 필요한 전체 방 상태·관측·기준 버전. 모델에 그대로 복사하지 않음 |

보조 출력은 구조화 스키마로 검증한다. 대상별 의미, 작성자, 근거 메시지와 인용 구간, 확인된 값, 미확인 값 및 필요한 정보의 출처를 구분한다. 보조 모델의 추천 도구 순위나 정답 표시는 Qwen에 전달하지 않는다.

- ‘응’, ‘아니 15만원’, ‘거기는 빼자’는 질문 답변·정정일 수 있으므로 짧다는 이유로 잡담 처리하지 않는다.
- 한 문장에 여러 요청이 있으면 대상별로 나눈다. ‘한강공원 말고 엑스포’의 반대·대안을 보존하고 장소 이름에 동작 표현을 붙이지 않는다.
- 새 발화와 참고용 과거 기록을 구분한다. 과거 맥락을 현재 작성자의 새 조건·찬성 근거로 재등록하지 않는다.
- 코드는 원문 포함 여부뿐 아니라 작성자·대상·항목 버전·값의 근거를 확인한다. 기존의 문장 전체 키워드 판정으로 대상별 찬반을 다시 덮어쓰지 않는다.
- 이전 기록에 있을 정보, 선행 도구 결과가 필요한 정보, 사용자에게 새로 물어야 하는 정보를 구분한다. 뒤의 두 경우를 해결하려고 대화 전체를 계속 재조회하지 않는다.
- 장소의 `mentioned`·지지 상태와 질문의 생성·해결 상태는 별도로 보존한다. 한 요청의 정보 부족이 다른 실행 가능한 요청을 막지 않는다.

## 4. 도구 호출 준비와 후보 구성

‘유효’는 현재 요청의 일부라도 수행할 수 있는 실제 도구 호출이 하나 이상 있다는 뜻이다. 도구가 요청에 적합하고, 필수 인자가 원문·방 상태·실제 관측에서 확보되며, 부정·정정·기존 조건과 충돌하지 않아야 한다. 단순히 JSON의 칸을 채울 수 있다는 뜻이 아니다.

| 분기 | 기본 후보 구성 |
| --- | --- |
| 유효한 도구 호출 가능 | 서로 다른 `tool_call` 최대 3개 + `cannot_answer` 1개 |
| 유효한 도구 호출 불가능 | `request_for_info` 최대 2개 + `cannot_answer` 1개 + `direct` 1개 |

### 후보 부족 예외

기본 목표는 4개지만 **실제로 성립하는 후보만 사용한다.** 유효 호출이 1~2개뿐이면 그 수만 제안하고, 필요한 질문이 하나뿐이면 하나만 제안한다. `cannot_answer`·`direct`도 내용이 성립할 때만 후보로 사용한다. 없는 호출·불필요한 질문·중복 문구·가짜 인자로 4개를 채우지 않는다.

후보가 하나면 ‘단일 유효 후보’로 기록하며 여러 대안을 비교했다고 표시하지 않는다. 후보가 전혀 없으면 Qwen을 호출하지 않고 새 작업 없음 또는 준비 실패로 구분해 기록한다. 미해결 요청은 지우지 않는다.

### 유형별 작성 규칙

- `tool_call`: 실제 도구명과 정확한 인자를 담는다. 도구·대상별 준비조건을 독립 확인하고, 동일한 도구·동일 인자는 중복 제거한다. 유효 호출이 3개를 넘으면 원문 요청의 대상 순서에 따라 이번 회차의 서로 다른 호출 3개를 제안하고 나머지는 미처리 작업으로 보존한다. 동률의 안정적 정렬은 구현에서 정하되 Qwen이 보지 못한 후보도 추적할 수 있게 한다.
- `request_for_info`: 현재 작업에 실제로 필요한 누락 값을 구체적으로 묻는다. 질문에는 대상·작성자·누락 필드·근거 메시지를 연결하고, 같은 질문을 표현만 바꾸어 두 개로 늘리지 않는다. 이미 열린 같은 질문을 중복 발행하지 않는다.
- `cannot_answer`: 등록된 기능으로 요청을 수행할 수 없다는 응답이다. 잡담이나 내부 처리 대기를 뜻하지 않는다.
- `direct`: 이미 확인된 사실만으로 답한다. 조회하지 않은 가격·시간·거리·장소 정보를 만들어내거나 언급을 합의·확정으로 바꾸지 않는다.

원본 후보는 모두 정답이라는 뜻이 아니다. Qwen 선택은 그대로 기록하되 실제 실행·발행 조건도 검사한다. 성립하지 않는 질문·미지원 주장이나 근거 없는 답변을 선택하면 보류하고 차순위 후보를 임의 실행하지 않는다.

## 5. 기존 5개 도구와 실행 계약

| 도구 | 후보 준비에 필요한 정보 |
| --- | --- |
| `search_places` | 근거 있는 검색어와 실제 방의 지역 |
| `get_place_details` | 이 방의 검색·관측에서 확인된 장소 ID |
| `get_car_route` | 확인된 출발·도착 참조와 해당 경로에 필요한 출발시각 |
| `build_itinerary` | 기존 계산 함수가 요구하는 방문·거점·조건·필요 경로 관측 |
| `calculate_costs` | 기존 계산 함수가 요구하는 가격·수량·분담·예산 및 준비 상태 |

기존 이름·인자·공급자·반환값·캐시·계산 의미는 유지한다. 인자는 보조 모델의 추측 대신 방 상태와 관측에서 조립한다. 일정·경비는 기존 canonical 인자 구성과 준비 검증을 사용하며, 이 작업에서 경비의 일정 의존성을 별도로 재설계하지 않는다.

- 인자 완성·검증은 Qwen 채점 전에 끝낸다. 빈 `{}`나 요약만 평가시킨 뒤 실행할 때 다른 인자로 확장하지 않는다.
- 동일한 방 상태와 기준 버전에서 만든 호출을 채점·실행·trace에 공통 사용한다. 실행 직전 관련 상태가 바뀌면 조용히 인자를 바꾸지 않고 다시 준비·판단한다.
- 누락된 필수 인자를 `null`·가짜 장소 ID·임의 시각으로 채우지 않는다. 명시적으로 nullable인 인자만 그 의미에 맞게 `null`을 사용한다.
- `departure_at=null`은 미래 여행의 출발시각 자동 주입이 아니다. 현재 경로와 여행 시각의 경로를 구분하며, 필요한 날짜·시각 관측을 다른 것으로 대체하지 않는다.
- 현재 코드의 장소 참조·지역 일치·canonical 계산 인자·준비 상태 검사를 유지한다. LangChain의 타입 검사만으로 이 업무 검증을 대체하지 않는다.
- 실제 도구 진입점은 기존 실행기 하나로 유지한다. 보조 모델이나 별도 프레임워크가 선택되지 않은 호출을 실행하지 않는다.

## 6. Qwen 판단과 상태 반영

제공된 베이스 모델·LoRA·토크나이저와 `judge_prompt`·`judge_scores`의 채점 방식은 유지한다. judge 채점에는 제공된 어댑터를 적용하고 모델 인스턴스와 호출 잠금을 재사용한다. 서비스는 실제 후보 수를 받는 기존 judge 함수를 연결하며, 제출용 4지선다 입출력과 패키지를 개편하지 않는다.

Qwen에는 동일한 요청·도구 정의 아래 실제 호출 또는 사용자 응답 형태로 직렬화한 후보를 전달한다. 후보 ID와 근거는 서버에서 매핑한다. 입력을 줄이기 위해 원시 관측의 중복·경로 배열 등 무관한 자료는 빼되, 도구 정의·필수 인자·판단을 바꾸는 원문 구간은 보존한다. 길이 초과로 이 정보가 잘릴 입력은 채점 전에 보완하거나 보류한다.

후보별 `yes - no` 원시 점수로 최종 선택하며 점수를 성공 확률로 표시하지 않는다. 임의의 점수 보정이나 검증되지 않은 0점 기준을 추가하지 않는다. 채점 실패·비유한 점수·부적격 선택은 명시적으로 보류하고, 제출 코드의 logprob/0번 fallback을 서비스 실행 권한으로 사용하지 않는다.

선택된 도구만 실행하거나 선택된 질문·미지원·직접 답변을 표시한다. 결과와 원문 근거를 기존 Backend 경계에서 반영하고, 요청별 진행 상태를 유지한다. 질문이 필요한 상태·처리 중·실행 완료·선택 보류를 같은 의미로 표시하지 않는다.

## 7. 기록과 검증

기존 trace에 필요한 정보만 연결한다. 별도 진단 API나 저장소는 만들지 않는다.

- 판단 회차와 기준 상태, 실제 후보 수·내용·근거, 후보별 점수와 선택 결과.
- 선택된 호출·인자와 실제 실행 결과. 개발자 수동 호출과 Qwen 선택 호출은 구분한다.
- 관찰 가능한 캐시·외부 API·로컬 계산 경로. 도구 선택만으로 외부 HTTP 성공을 주장하지 않고 관찰하지 못한 정보는 미확인으로 남긴다.
- 보조 모델·Qwen·도구·전체 처리 시간과 입력 크기. 비밀값이나 모델의 비공개 추론은 넣지 않는다.

구현 후에는 관련 기존 회귀와 다음 서비스 상황을 확인한다.

1. 지역·장소가 명확하면 불필요한 문맥 보완·질문 없이 검색 후보가 생기고 Qwen 선택이 실제 실행으로 이어진다.
2. ‘한강공원 말고 엑스포’, ‘아니 15만원’, ‘응’에서 대상·정정·질문 연결과 작성자 근거가 보존된다.
3. 이전 기록으로 해결할 누락과 사용자에게 물어야 할 누락을 구분하며 질문은 중복 발행하지 않는다.
4. 필수 인자 부족·실제 미지원·단독 잡담·후보 0/1/2개에서 가짜 후보나 임의 도구 실행이 없다.
5. Qwen이 평가한 호출과 실제 실행한 호출이 같고, 오래된 상태·채점 실패에서는 실행을 보류한다.
6. 실제 Qwen의 선택·호출을 trace로 확인하고, 같은 대화에서 입력 축약 전후 선택 품질과 전체 p50/p95·문맥 확대율·실제 채점 후보 수를 비교한다.

## 8. 구현 순서

1. 보조 출력과 최소 상태·관련 문맥 조회 계약을 연결한다.
2. 기존 인자 조립·검증을 재사용해 분기별 후보와 후보 부족 예외를 구현한다.
3. 제공된 Qwen judge를 최종 선택 단계에 연결한다.
4. 선택된 행동만 기존 실행기에 전달하고 결과·요청별 상태·trace를 연결한다.
5. 관련 회귀와 실제 모델·도구 실행을 검증하고 관측한 결과만 기록한다.

이번 문서 수정은 위 구현이 완료되었다는 보고가 아니다.

## 구현 시 확정한 참조 요청 처리

현재 발화의 “내가 고른 두 곳”처럼 대상이 과거 기록에 있는 경우, 보조 출력의 `analysis.requests`에 현재 요청과 대상 이름·배제 이름·원문 근거만 구조화한다. 코드는 작성자와 제공된 과거 인용을 검증하고 같은 방의 기존 관측에서 유일한 참조로 해소한다. 과거 찬반은 새 찬반으로 등록하지 않는다. 해당 조회 요청이 있으면 그 대상의 실제 상세 조회 후보만 제시하며 관련 없는 계획 도구를 섞지 않는다.

요청별 완료·대기 참조는 기존 room JSON에 보관한다. 새 사용자 입력은 해당 회차에서 우선하고, 저장된 요청은 새 입력이 없는 후속 실행에서 재개한다. 같은 소유자의 명시적 배제·미해결 대상 해소는 이전 요청을 superseded로 남긴다. 완료 상태와 원래 근거는 보존한다.
