# Frontend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 사람 채팅과 Agent가 갱신하는 공동 여행 상태를 분리하고, 4명이 같은 전체 여행안을 검토·확인할 수 있는 최소 HTML 화면을 만든다.

**Architecture:** 같은 origin에서 제공하는 HTML/CSS/ES modules가 Backend의 HTTP DTO와 방별 SSE 한 연결만 사용한다. 공동 상태는 `RoomSnapshot`을 기준으로 교체하고, 선택 장소·지도 확대·표시 탭만 브라우저의 개인 상태로 둔다. Backend 준비 전에는 같은 계약의 명시적 fixture 모드로 화면을 검증한다.

**Tech Stack:** HTML, CSS, browser ES modules, Fetch, EventSource, Kakao Maps JavaScript SDK. React·WebSocket·프런트 빌드 도구는 도입하지 않는다.

**Spec:** [공동 여행 Agent MVP 설계](../specs/2026-11-18-travel-agent-design.md), [FE·BE·AI 공통 계약](../../contracts/travel-api.md).

## S1 독립 실행 경계

- 최신 실행 방식은 [3세션 병렬 계획](2026-11-18-three-session-plan.md)을 따른다. S1은 frontend/**와 [자기 검증 기록](../../verification/frontend.md)만 수정한다.
- **F1-F5를 모두 Backend 없이 fixture transport로 먼저 완료한다.** 아래 live 확인은 S2와 연결하는 G3/G4의 별도 통합 검증이며 해당 코드가 나올 때까지 개발을 멈추지 않는다.
- [동결 JSON 예제](../../contracts/examples/README.md)를 자기 frontend/fixtures에 복사·변형한다. 원본 계약/예제·공통 체크리스트·루트 README·의존성은 수정하지 않는다.
- fixture는 정해진 DTO 전이 시나리오를 재생한다. 실제 다수결/확정 알고리즘을 FE에 복제하지 않는다. 사용자 전환을 지원하는 개발 시나리오로 4인 상태를 확인하되 실제 인증·SSE 성공이라고 기록하지 않는다.
- 외부 지도 키가 없으면 지도 adapter 대역/좌표·경로 목록으로 렌더링 입력과 개인 상태를 먼저 검증한다. 실제 Kakao SDK는 준비되는 시점에 G3/G4에서 확인한다.
- 정적 서버 5173과 frontend/.artifacts를 사용한다. 다른 작업 공간의 DB·포트·가상환경을 공유하지 않는다.

## Global Constraints

- 이 문서는 구현 계획이다. 현재 작업에서 제품 코드·실행 스크립트·Git 초기화·커밋·push·PR을 만들지 않는다.
- 실제 구현을 요청받으면 `AGENTS.md`와 `.local/skills/trip-agent-small-commits/SKILL.md`를 다시 읽는다. 실행 로직은 약 300자 단위의 작동하는 작은 기능으로 구현·검증·커밋한다.
- 국내 한 도시, 대표 데모 여수·4명·1박 2일. 자동차만 지원한다.
- `frontend/`, `backend/`, `ai/` 경계를 지키고, FE는 모델·DB·공급자 비밀 키에 직접 접근하지 않는다.
- JSON snake_case, ID 문자열, 시간 ISO 8601(타임존 포함), 날짜 YYYY-MM-DD, 금액 KRW 정수/미확인 null, 이동시간 초·거리 m, 좌표 latitude/longitude.
- 화면은 사람 채팅 왼쪽 약 30%, 오른쪽 약 70%에 조건·질문·공동 항목·전체 동선·선택 장소·경비를 배치한다. 별도 모바일 UI는 범위 밖이다.
- `mentioned`는 빨강, `supported`는 노랑, `confirmed`는 초록이다. FE가 지지 인원·문장·단순 선택으로 이 상태를 재계산하지 않는다.
- 노랑 기준은 현재 참가자 과반수 `floor(N/2)+1`이며 Backend가 `support_threshold`와 `state`로 제공한다. 초록은 같은 전체 여행안에 대한 전원 확인 후에만 표시한다.
- 충돌 `!`는 색상과 독립된다. 개인 필수 조건은 소유자만 수정·확인하며 다수 지지로 완화하지 않는다.
- `confirmation_target`의 네 version과 `content_hash`를 함께 취급한다. 화면이 검토 중인 대상을 임의로 최신 초안으로 바꾸지 않는다.
- API 가격·영업시간, 추정, 사용자 입력, 미확인, fixture를 구별한다. fixture 성공은 실제 API·Qwen 성공이 아니다.
- 범위는 기능 확인용 화면과 핵심 수동 검증이다. 범용 상태 프레임워크·복잡한 오류 체계·예약·결제는 만들지 않는다.

## F2: 계정·방·여행 입력·사람 채팅·SSE

**Files:** Create `frontend/src/events.js`; Modify `frontend/index.html`, `frontend/styles.css`, `frontend/src/{api,fixture-api,state,room}.js`, `frontend/README.md`.

**Interfaces:**
- `room.js`: `startRoomApp() -> Promise<void>`, `enterRoom(snapshot:RoomSnapshot) -> void`, `refreshRoom(room_id:string) -> Promise<void>`, `renderRoom(snapshot:RoomSnapshot) -> void`.
- `events.js`: `openRoomEvents(room_id, {onMessage,onRoomUpdated,onAgentStatus,onPlanConfirmed,onReconnect}) -> close()`. 각 handler는 공통 계약의 해당 이벤트 `data`를 받는다.
- `User {id,name,email}`, `Member {user_id,name}`, `Message {id,room_id,seq,author_id,text,created_at}`. 메시지 author는 항상 사람이다.
- 계정: `POST /api/auth/register {name,email,password}`, `POST /api/auth/login {email,password}` → `User`; `GET /api/auth/me` → `User`; `POST /api/auth/logout` → `{ok:true}`.
- 방: `POST /api/rooms {title,...TripConfig}`, `POST /api/rooms/join {invite_code}`, `GET /api/rooms/{room_id}`, `PATCH /api/rooms/{room_id}/trip {수정할 TripConfig 필드}` → `RoomSnapshot`.
- 대화: `POST /api/rooms/{room_id}/messages {text}` → `Message`; `GET /api/rooms/{room_id}/messages?after_seq=0` → `{messages,last_seq}`; `GET /api/rooms/{room_id}/messages/{message_id}` → 근거 `Message`.
- SSE `GET /api/rooms/{room_id}/events`: `message.created {room_id,seq,message}`, `room.updated {room_id,seq,changed}`, `agent.status {room_id,seq,status}`, `plan.confirmed {room_id,seq,target}`.
