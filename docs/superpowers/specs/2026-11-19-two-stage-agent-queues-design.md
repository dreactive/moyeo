# 보조 모델 선처리와 Qwen 실행을 분리하는 2단계 큐 설계 검토안

## 1. 목적

단체 채팅에서 에이전트가 판단하거나 도구 응답을 기다리는 동안, 이후에 들어온 발화를 보조 모델이 미리 해석하도록 처리 단계를 분리한다.

핵심 제안은 다음과 같다.

> 메시지 수신 큐와 보조 모델의 해석 결과 큐를 분리하고, 보조 모델의 선처리를 기존 Qwen·도구 실행과 겹쳐 진행한다.

이 문서는 실험 결과를 바탕으로 한 설계 검토 초안이다. 현재 단계에서는 코드를 수정하지 않는다.

## 2. 현재 확인한 처리 구조

현재 확인한 로컬 코드에서는 보조 모델 호출과 Qwen 호출 모두 비동기 함수 안에서 스레드로 넘겨 실행한다.

하지만 작업 큐의 소비자가 한 작업의 전체 처리를 기다린 뒤 다음 작업을 꺼내므로, 호출이 비동기라는 사실만으로 다음 발화의 선처리가 자동으로 진행되지는 않는다.

```text
메시지 수신
    ↓
현재 작업 큐
    ↓
보조 모델 해석
    ↓
후보 생성 → Qwen 판단 → 도구 실행 → 결과 반영
    ↓
전체 처리 종료 후 다음 작업 시작
```

추가로 확인한 사항:

- 로컬 Qwen 모델의 추론은 공유 잠금으로 직렬화되어 있다.
- 외부 보조 모델 API 호출과 외부 도구 응답 대기는 로컬 Qwen 추론과 다른 자원을 사용한다.
- 새 메시지가 도착하면 기존 실행의 상태 스냅샷이 오래된 것으로 판단될 수 있다.
- 이미 시작된 외부 도구 호출은 이후 실행이 무효화되어도 끝까지 수행될 수 있다.
- 현재 trace에는 단일 `active_run_id`를 전제로 한 부분이 있어, 작업 단계가 겹치면 추적 구조도 검토해야 한다.

최종 설계 전에는 실제 배포 버전과 위 코드 구조가 일치하는지 확인해야 한다.

## 3. 실험에서 확인한 사실

### 3.1 에이전트 완료를 기다린 23개 발화

| 항목 | 측정값 |
|---|---:|
| 보조 모델 추출 시간 평균 | 약 3.15초 |
| 발화 입력부터 완료 확인까지의 관측 대기 평균 | 약 7.76초 |
| 긴 대기 사례 A | 관측 28.72초 / 추출 2.92초 |
| 긴 대기 사례 B | 관측 37.34초 / 추출 2.59초 |

관측 대기에는 상태 확인을 위한 폴링과 자동화 지연이 포함되어 있다. 순수한 서버 실행 시간과 동일하지 않다.

따라서 다음과 같이 해석한다.

- 보조 모델 선처리를 다른 작업과 겹칠 여지는 있다.
- 긴 대기 전체를 보조 모델의 지연으로 설명할 수는 없다.
- 위 평균값만으로 예상 단축 시간을 계산하거나 성능 향상을 보장할 수는 없다.

### 3.2 에이전트 완료를 기다리지 않은 연속 입력

부산 시나리오에서는 10개 발화가 약 4.43초 동안 입력되었다.

확인한 실행에서는 앞선 실행들이 `held` 상태가 되었고, 이후 실행이 누적된 발화를 처리했다. 메시지 누락이나 오래된 실행 결과의 상태 덮어쓰기는 관측되지 않았다.

다만 일부 의미 처리 결과가 기대와 달랐다. 이것이 빠른 입력 때문인지는 동일 시나리오를 순차 입력한 대조 실험 없이 단정할 수 없다.

## 4. 제안 구조

```text
채팅 메시지 저장
    ↓
[큐 1: 해석 대기 메시지]
    ↓
보조 모델 작업자
    ├─ 발화에서 사실·의도 후보 추출
    ├─ 원문·작성자·순서·해석 근거 연결
    └─ 결과 전달 후 다음 메시지 처리
    ↓
[큐 2: 해석 완료 결과]
    ↓
후속 실행 작업자
    ├─ 최신 방 상태 조회
    ├─ 해석 결과의 유효성 검증
    ├─ 실행 후보 생성
    ├─ Qwen 판단
    ├─ 도구 실행 및 필요 시 재판단
    └─ 상태·응답 반영
```

초기 검토안은 다음과 같다.

- 보조 모델 작업자: 1개
- 후속 실행 작업자: 1개
- 로컬 Qwen 동시 추론: 기존 1개 제한 유지
- 두 작업자는 독립적으로 동작

보조 모델 작업자는 큐 2에 결과를 넣은 뒤, 해당 결과의 Qwen·도구 처리가 끝날 때까지 기다리지 않는다.

### 기대하는 동작 예시

```text
시간 →
후속 작업자: [발화 A 판단][발화 A 도구 대기........][결과 반영][발화 B 판단]
보조 작업자:             [발화 B 해석][발화 C 해석]
```

이 구조의 초기 개선 범위는 보조 모델 선처리와 후속 처리를 겹치는 것이다.

후속 작업자가 도구를 기다리는 동안 다른 요청의 Qwen 판단까지 실행하려면, 후속 실행을 중단·재개하는 별도 스케줄링 설계가 필요하다.

## 5. 각 큐와 작업자의 책임

| 구성 요소 | 책임 |
|---|---|
| 큐 1 | 저장된 메시지의 해석 작업을 전달하고 원문 순서를 보존 |
| 보조 모델 작업자 | 발화에서 사실·의도 후보와 문맥 의존성을 추출 |
| 큐 2 | 출처와 해석 기준이 포함된 준비 결과를 전달 |
| 후속 실행 작업자 | 최신 상태를 기준으로 검증·후보 생성·Qwen 판단·도구 실행·반영 수행 |

큐 2에는 오래된 상태에서 확정한 실행 계획이나 Qwen 프롬프트를 그대로 넣기보다, 재검증할 수 있는 해석 결과를 넣는 방향을 우선 검토한다.

큐 2의 논리적 데이터 항목 예시:

- 작업 ID와 방 ID
- 원문 메시지 ID, 작성자, 방 내 순서
- 처리한 메시지 범위
- 추출한 사실·의도 후보
- 해석에 사용한 상태 버전 또는 문맥 기준
- 문맥 의존 여부와 재검증에 필요한 정보
- 추출 상태, 시각, 재시도 정보

구체적인 필드와 저장 형식은 설계 단계에서 확정한다.

## 6. 반드시 유지할 처리 규칙

### 6.1 같은 방의 의미와 순서를 보존한다

참여자별로 대화를 분리하면 서로의 발화를 참조하는 표현을 해석하기 어렵다.

예를 들어 다음 메시지는 함께 해석해야 한다.

1. 도윤: “오동도에 가자.”
2. 수빈: “거긴 빼고 자산공원으로 하자.”

선처리는 미리 수행할 수 있지만, 상태 반영은 방의 발화 순서와 변경 관계를 지켜야 한다.

참여자 수를 그대로 스레드 수나 모델 동시 실행 수로 사용하지 않는다.

### 6.2 선처리 결과는 실행 전에 재검증한다

다음 두 종류를 구분할 필요가 있다.

- 명시적인 정보: “내 예산은 15만원이야.”
- 문맥에 의존하는 정보: “거긴 취소하자.”

문맥 의존 결과는 앞선 발화의 처리 결과에 따라 다시 해석해야 할 수 있다. 명시적인 정보도 이후 정정 발화가 있는지 확인해야 한다.

재검증에 실패한 결과는 그대로 실행하지 않고 재해석 또는 보류한다.

### 6.3 새 메시지 도착에 따른 무효화 범위를 설계한다

현재처럼 새 메시지가 도착했다는 이유만으로 기존 실행 전체를 무효화하면 선처리한 결과도 반복해서 버릴 수 있다.

다음 항목의 유효성을 구분하는 방향을 검토한다.

- 원문에서 추출한 정보
- 특정 장소에 대한 검색 결과
- 현재 합의와 제약을 반영한 실행 후보
- 최종 일정과 사용자 응답

예를 들어 장소 운영시간 조회 결과는 재사용할 수 있어도, 이후 취소된 장소를 포함한 여행안은 다시 계산해야 한다.

유효한 도구 결과를 보관하는 것과 오래된 계획을 현재 상태에 반영하는 것은 별도로 판단한다.

### 6.4 추출 완료와 전체 처리 완료를 구분한다

최소한 다음 상태를 구분해야 한다.

```text
수신 → 해석 대기 → 해석 완료 → 실행 대기 → 실행 중 → 처리 완료
```

뒤 메시지의 해석이 끝났다고 앞 메시지의 도구 작업까지 완료된 것으로 기록하면 안 된다.

기존 커서와 처리 완료 조건을 그대로 사용할 수 있는지 검토하고, 필요하면 추출 진행과 실행 완료를 별도로 관리한다.

### 6.5 재시도해도 중복 반영을 막는다

실패·재시작·재전달 시 다음을 구분한다.

- 추출을 다시 수행해도 되는 작업
- 이미 상태에 반영된 작업
- 이미 호출된 외부 도구
- 결과는 받았지만 아직 반영하지 않은 작업

메시지·작업 ID를 기준으로 중복 상태 반영을 막고, 도구 호출의 재시도 가능 여부도 정의한다.

## 7. 큐 적체와 운영 정책

설계 단계에서 다음 정책을 정한다.

- 큐 크기와 적체 시 처리 방식
- 같은 방의 연속 메시지를 묶는 기준
- 묶어서 처리할 때의 최대 대기 시간과 메시지 수
- 여러 방 사이의 공정한 작업 배분
- 보조 모델 및 외부 도구 API의 동시 호출 제한
- 실패·시간 초과·재시도의 상한
- 프로세스 재시작 후 미완료 작업 복구 방식

메시지를 묶더라도 원문 ID, 작성자, 순서, 정정·취소 관계를 보존한다.

큐의 메모리 저장 또는 영속 저장 여부는 현재 배포 구조와 복구 요구사항을 확인한 뒤 선택한다.

## 8. 실행 이력과 시간 측정

두 단계가 동시에 동작해도 메시지에서 최종 결과까지 연결해서 추적할 수 있어야 한다.

공통 식별자:

- 방 ID
- 메시지 ID 또는 메시지 범위
- 추출 작업 ID
- 후속 실행 ID
- 도구 호출 ID

주요 측정 시점:

1. 메시지 수신·저장
2. 큐 1 진입
3. 보조 모델 시작·종료
4. 큐 2 진입·이탈
5. Qwen 판단 시작·종료
6. 도구 호출 시작·종료
7. 상태 반영 및 사용자 응답 완료

이를 통해 큐 대기, 모델 실행, 도구 대기, 최종 반영 시간을 구분한다.

기존 단일 `active_run_id` 방식이 겹치는 작업의 trace를 누락시키지 않도록 추적 구조도 함께 검토한다.

## 9. 검증 방법

동일한 시나리오를 사용해 다음 조건을 비교한다.

| 조건 | 목적 |
|---|---|
| 현재 구조 + 발화마다 완료 대기 | 의미 처리 기준 결과 확인 |
| 현재 구조 + 연속 입력 | 기존 동시 입력 동작 확인 |
| 제안 구조 + 연속 입력 | 선처리 중첩의 효과와 부작용 확인 |

비교 항목:

- 메시지 누락 여부
- 발화 순서와 작성자 정보 보존
- 정정·취소·찬반·예산의 처리 결과
- 오래된 결과의 상태 덮어쓰기 여부
- 중복 상태 반영과 중복 도구 호출
- 단계별 대기 시간과 실행 시간
- 최종 응답 시간과 긴 대기 사례
- 무효화된 작업 수와 재처리 비용

성능이 개선되어도 대화의 의미 처리 결과가 달라지면 원인을 확인해야 한다.

## 10. 이번 구조 개선과 별도로 다룰 문제

여수 당일 여행 실험에서 확인한 다음 문제는 별도 원인 분석과 수정이 필요하다.

- 이미 입력한 날짜·시간을 상태에 반영하지 못한 문제
- 출발·도착 장소와 체류시간 등의 정보 누락
- 운영시간·주차요금 등 필요한 정보의 미확보
- 최종 여행안이 생성되지 않은 문제

두 큐로 처리 단계를 나누는 것만으로 이러한 의미 추출·상태 반영 문제까지 해결된다고 가정하지 않는다.

## 11. 다음 설계 단계에서 결정할 사항

1. 큐 1과 큐 2의 데이터 계약
2. 방별 순서 보장과 메시지 묶음 처리 정책
3. 선처리 결과의 재사용·무효화·재해석 기준
4. 추출 진행과 전체 처리 완료의 상태·커서 정의
5. 실패·재시도·재시작 시 복구 및 중복 방지 방식
6. 작업별 trace와 단계별 시간 측정 방식
7. 현재 배포 구조에 맞는 큐 저장 방식
8. 초기 적용 범위와 비교 실험의 통과 기준

우선은 보조 모델 작업자와 기존 후속 실행을 분리하는 작은 범위로 설계한다. Qwen 동시 추론 확대와 도구 대기 중 다른 후속 작업 실행은 측정 결과를 보고 별도로 검토한다.

## 12. 구현 시 확정한 운영 정책

사용자의 구현·일괄 커밋·원격 develop push 지시에 따라 위 검토안을 구현한다. 검토 당시의 코드 미수정 문구는 이번 구현 지시로 대체한다.

- 최신 origin/develop(b0cb8f0)을 기준으로 별도 작업 공간에서 수행하며 원래 서버·DB·미커밋 환경설정 변경은 건드리지 않는다.
- 기존 records 테이블에 방별 작업과 추출/실행 진행을 저장한다. 20개 이하의 원문 범위를 예약하고 원문 ID·작성자·순서를 고정한다. 기본 배치 대기는0ms다.
- 보조 작업자1개와 후속 실행 작업자1개. Qwen 공유 잠금은 유지한다. SQLite를 backlog로 사용하며 메모리는 알림만 보관한다. 준비 결과는 전역64개/방별8개로 제한한다.
- 방별 각 단계 FIFO, 방 사이 round robin. 뒤 발화의 추출은 앞 발화의 도구 대기와 중첩되지만 같은 방의 반영은 순서대로 한다.
- 큐2에는 원시 구조화 해석, 불변 원문 출처, 해석 기준·선택한 과거 문맥과 시각을 저장한다. 실행 후보/프롬프트는 저장하지 않는다.
- 최신 상태에서 다시 grounding한다. 명시적 사실은 재사용하고, 문맥 의존 기준이 달라지면 보조 큐를 통해 최대1회 재해석한다. 실행 작업자는 보조 API를 직접 호출하지 않는다.
- 최신 발화가 대기 중이면 오래된 배치는 검증된 사실과 미처리 요청만 순서대로 반영하고 도구/여행안 실행은 최신 입력까지 따라잡은 뒤 진행한다. 이후 정정·취소가 있는 오래된 호출을 재시도로 되살리지 않는다.
- 원래 실행 cursor는 상태 반영 후에만 이동하고 추출 cursor는 별도로 기록한다. 작업별 실패/보류를 남겨 높은 cursor가 개별 실패를 숨기지 않게 한다.
- 추출·실행 자동 시도는 각각최대2회, 문맥 재해석은최대1회, 후속 도구 회차 이어가기는최대2회다. 수동 재시도는 새 명시적 작업이다. 타임아웃 기본값은 추출120초/실행300초다.
- 성공한 읽기 전용 도구 반환을 호출 ID와 함께 checkpoint한다. 재시작 시 적합성 검사를 유지해 재사용한다. 응답을 받기 전에 끊긴 외부 읽기 요청은 중복 여부를 알 수 없으므로 제한된 재호출이 가능하다. 외부 정확히1회 호출을 보장하지 않는다.
- room/run/applied fence와 완료 작업/cursor를 같은 SQLite put_many로 저장해 상태 중복 반영을 막는다. 작업이 삭제된 방에 대한 늦은 결과는 거절한다.
- 기존 공개 agent_status state를 유지하고 단계/큐/커서를 additive agent_pipeline 정보로 제공한다. 추출·실행별 run 연결 trace와 재시도별 execution_id/attempt를 남긴다. 개인 키·claim token·비공개 추론은 기록하지 않는다.
- C-revised2 의미 처리 규칙, 공급자 매칭 정책, Qwen weight·LoRA·judge·원시 점수 선택은 이번 변경 범위에 넣지 않는다.
