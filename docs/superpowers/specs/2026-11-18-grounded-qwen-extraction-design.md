# 로컬 Qwen 스키마·근거 기반 추출 설계안

상태: 검토용 초안. 사용자 요청은 개선 계획 작성이며 구현·설치·모델 재실행·커밋은 시작하지 않는다.

## 목적과 현재 근거

로컬 Qwen을 유지하고 자연어 장소·조건 추출을 구조화한다. JSON 형식 오류와 근거 없는 조건을 구분하여 처리하고, 실패를 성공처럼 표시하지 않는다.

- 현재 `ai/models/qwen_generation.py:6`은 자유 생성 문자열을 `json.loads()`로 읽는다.
- `ai/extraction.py:26`은 조건의 메시지 ID/발화자는 검사하지만 조건 값의 의미 근거는 검사하지 않는다. 장소는 `:34`의 원문 부분 문자열 비교에 의존한다.
- `ai/assistance.py:7`의 장소 보조는 제한된 문장 패턴과 단어 목록만 지원한다.
- `ai/runner.py:17`은 ValueError를 빈 출력으로 바꾸고, `:53`은 장소·질문이 없으면 done으로 처리한다.
- `backend/services/agent_jobs.py:13`과 `:94`의 입력은 미처리 메시지이며, 실패 원문과 이전 대화는 같은 개념이 아니다.
- 현 브랜치는 후보 생성 전용이다. 이 작업으로 자동 도구 실행·일정 생성·채점 루프를 복원하지 않는다.

## 검토한 접근

| 접근 | 장점 | 한계 | 제안 |
|---|---|---|---|
| 프롬프트 + Pydantic 사후 검증 + 1회 재시도 | 의존성·생성 변경이 작음 | 문법 오류는 계속 생성할 수 있음 | 비교 기준 |
| Pydantic + JSON Schema 기반 토큰 제한 + 근거 검증 | 기존 Transformers Qwen에서 생성 형식과 사후 검증을 연결 | 토크나이저 호환성·속도 검증 필요 | 권장 초안 |
| 별도 로컬 추론 서버 도입 | 구조화 API를 제공하기 쉬움 | 실행·배포 구조와 GPU 관리 변경이 커짐 | 이번 범위 제외 |

권장안을 사용자가 선택한 것으로 간주하지 않는다. 구현 시 첫 호환성 검증을 통과해야 채택한다. 호환성/속도 기준에 실패하면 결과와 사후 검증 방식의 한계를 보고하고 접근을 다시 결정한다. 조용히 형식 제한을 해제하지 않는다.

## 처리 구조

미처리 메시지와 읽기 전용 맥락 → 로컬 Qwen의 제한된 JSON 생성 → Pydantic 구조 검증 → 인용문/발화자/값 검증 → 기존 AgentResult로 변환 → Backend 반영과 상태 기록.

### 형식

- 새 `ai/extraction_schema.py`에서 Pydantic v2 모델과 `model_json_schema()`를 단일 기준으로 사용한다. 최상위 목록은 필수이며 값이 없으면 명시적인 빈 목록을 출력한다. `extra=forbid`, 엄격한 타입, 문자열/목록 길이 상한을 둔다.
- 내부 `ExtractionBatch`는 `message_assessments`, `constraint_proposals`, `item_proposals`, `support_observations`를 가진다. assessments는 각 미처리 메시지를 정확히 한 번 포함하고 의도를 비어 있지 않은 `intents` 목록(chitchat/place/condition/support/region/unclear)으로 분류한다. 한 메시지의 장소·조건 등 복수 의도를 허용하고 의도별 수용/거절을 기록한다. 장소/조건 의도인데 유효 사실이 없으면 완료로 위장하지 않는다. 이 분류도 모델 판단이므로 실제 모델 평가가 필요하다.
- 내부 제안은 `EvidenceQuote(message_id, quote)`를 요구한다. quote는 원문에 존재하는 연속 부분 문자열이며 비어 있을 수 없다. 내용의 사실성은 이 검사만으로 보장되지 않는다.
- 장소는 `mention_text`(원문 표현)와 `title`(표시 이름)을 분리한다. source ID와 client_ref는 검증한 뒤 코드가 결정한다. 검증에 통과한 기존 외부 제안 형태로 변환할 때만 내부 필드를 제거한다.
- LM Format Enforcer의 `JsonSchemaParser`와 Transformers `prefix_allowed_tokens_fn` 연결을 검토한다. 추출 phase에만 적용한다. 토크나이저 데이터는 재사용하되 parser/생성 상태는 호출마다 새로 만들어 방 간 누출을 막는다. 출력 길이 제한이나 중단으로 미완성된 결과는 여전히 실패다.
- 베이스 모델, tokenizer, adapter 파일과 현재 adapter 비활성 생성 정책은 그대로 비교한다. adapter 켜기는 별도 실험이다. 원격 모델·다운로드를 도입하지 않는다.

### 근거 검증

- 새 제안의 근거는 미처리 메시지에 한정한다. 과거 대화 최대 20개는 `conversation_context`라는 별도 선택 필드에 넣으며, 상태 참조와 함께 읽기 전용으로 표시한다. 다른 방의 문맥을 넣지 않는다. 누락 시 빈 목록으로 처리한다.
- 조건은 메시지 작성자와 소유자가 같아야 한다. 의미 검증은 인용문뿐 아니라 원문 메시지 전체를 검사하여 잘라낸 인용문이 부정·가정·타인 발언을 숨기지 못하게 한다. 다른 사람의 말 전달·가정·부정·철회·질문을 확정 hard 조건으로 변환하지 않는다. 모호한 경우 거절 사유를 남기고 needs_input으로 처리한다.
- 첫 자동 정규화 지원은 현재 제품이 소비하는 `budget`, `budget_krw`, `return_by`다. 예산 표현의 단위·개인/공유 범위, 시간 표현의 시각·마감 의도를 코드에서 확인하고 정규화한 값과 제안 값을 비교한다. 단순 숫자 존재나 인용문 존재만으로 통과시키지 않는다.
- 내부 조건 key는 길이가 제한된 문자열로 두어 미지원 key도 출력·거절 가능하게 한다. decoder가 지원 enum 중 다른 key를 억지로 선택하게 제한하지 않는다. 등록되지 않은 조건 key는 `unsupported_constraint_key`로 보류하며 새로운 hard 조건으로 저장하지 않는다. 기존 저장 조건은 변경하지 않는다. 기존 평가의 다른 조건 종류는 구현 전 목록화하고 필요한 validator를 추가하거나 명시적 보류 기대값으로 검토한다.
- 장소는 고유명사 단어 목록을 요구하지 않는다. mention_text가 quote 및 원문에 포함되어야 하고, title은 Unicode/공백 정규화 후 mention_text와 같아야 한다. Unicode/공백 정규화 차이만 안전하게 비교하고, 별칭·주소·좌표·지점 정보는 만들어내지 않는다. '여수 가는 건 어때'는 지역 제안으로 분류하며 POI나 방 설정을 자동 생성하지 않는다.
- 기존 support의 발화자·항목 버전·명시적 지지/반대 규칙을 유지한다. 애매한 좋아/전원 대리 지지는 기존 질문 흐름을 따른다.
- 기존 규칙 보조가 이 검증을 우회하지 못하게 한다. JSON 형식 실패를 보조 결과로 성공 처리하지 않는다. 모델이 정상 스키마를 반환했을 때의 보조 제안도 같은 evidence/값 검증 경로를 거친다.

### 실패·거절·처리 포인터

- 스키마/출력 잘림 오류: 같은 입력과 짧은 검증 오류로 최대 1회 재시도한다. 두 번째도 실패하면 결과를 적용하지 않고 처리 포인터를 보존한다. 배치의 메시지 ID와 오류 코드는 DB `failed-extraction:<room_id>` 목록에 남긴다. 일반 작업은 이 실패 목록을 제외한 미처리 메시지에서 최대20개를 선택하며, 실패 메시지를 제외하기 전에 20개로 자르지 않는다. 이후 정상 메시지가 포인터를 전진시켜도 실패 목록은 남는다. 기존 수동 재계획 요청은 실패 목록 최대20개를 명시적으로 재시도하고 성공한 ID만 복구 처리한다. 재처리한 과거 메시지 때문에 포인터가 뒤로 가지 않게 방 메시지 순서의 최대 위치로만 갱신한다. 실패 배치를 자동 재등록하지 않는다. 이미 큐에 있던 일반 작업은 refresh 시 실패 목록을 반영하며 처리할 메시지가 없으면 모델을 다시 호출하지 않는다. 원시 모델 응답이나 사고 과정은 trace에 넣지 않는다. 실패 기록은 message_id/issue code/attempts/run_id/복구 상태만 저장한다.
- 의미 근거 없는 제안: 해당 제안만 제외하고 나머지 검증된 사실은 적용한다. 평가를 마친 배치의 포인터는 전진하되 `filtered`와 제외 사유를 사용자 상태/trace에 표시한다. 이는 파싱 실패로 메시지를 잃는 것과 구분한다. 의미 검증 실패를 고치겠다며 반복 호출하지 않는다.
- 정상 인사: 명시적인 빈 목록, chitchat 평가, 검증 성공일 때만 추가 사실 없이 done이 될 수 있다. 장소/조건/region/unclear 의도인데 사실이 없으면 needs_input과 재표현 안내를 표시한다. 한 메시지에서 장소가 수용되어도 조건이 거절/보류되면 filtered와 needs_input을 유지한다.
- 선택적인 AgentResult `extraction_report`를 추가한다: `{status:ok|filtered|failed, issue_codes:string[], rejected_message_ids:string[], attempts:int}`. 없으면 기존 fixture/port 계약대로 처리한다. 내부 quote는 외부 필수 제안 계약에 추가하지 않는다.
- `failed` 결과에는 부작용 제안과 처리 ID가 없어야 한다. Backend는 독립적으로 반영·포인터·잔여 메시지 자동등록을 차단한다. 일반 예외와 오래된 결과 역시 완료로 표시하지 않는다.
- 기존 상태 enum을 유지하고 agent_status.label을 사람에게 의미 있는 문장으로 설정한다. frontend는 기존 label 경로를 사용한다. 개발 trace에는 decoder_mode/schema_version/건수/issue code/소요 시간만 기록한다.

## 완료 기준

- 인사에서 예산/귀가시간/장소가 생기지 않는다. '안녕'과 12:00 조건의 조합은 반드시 거절한다.
- '전남대학교 가는 건 어떄?', '롤링 파스타에서 점심 먹자', '오동도 가자'의 실제 Qwen 추출이 새 장소와 정확한 근거를 반환한다. 지지 여부는 별도 규칙을 따른다.
- '내 예산은 20만원', '난 16시까지 역에 도착해야 해'는 본인 조건으로 정규화한다. 부정·가정·타인 인용·시각 없는 식사 문장에서 hard 조건을 만들지 않는다.
- 잘린/형식 불일치 결과는 1회 재시도 후 failed로 끝나며 DB proposal 반영/처리 포인터 전진/무한 재등록이 없다.
- 일반 단위·통합 검증과 실제 Qwen 검증을 분리한다. 실제 회귀 집합 32개(장소8/조건8/지지8/무정보·부정8)에서 인용문·소유자·값 위반 저장 0건, 핵심 3개 장소 재현 성공, 정상 완료 출력의 구조 검증률 100%를 요구한다. 나머지 정확도/거절률은 입력별 기록하고 오류를 숨기지 않는다.
- 동일 모델·환경의 자유 생성 대비 p50/p95, 출력 토큰, 잘림/실패/재시도율을 기록한다. warm p95 지연이 2배를 넘으면 채택 전 개선·접근 재검토 대상으로 남긴다. 표본 32개의 한계를 명시한다.
- 기존 방의 잘못된 조건은 자동 삭제하지 않는다. 실험은 익명화한 복사 입력/별도 DB에서 수행한다.

## 구현자 관점 검토 반영

실패 20개로 인한 후속 입력 차단, 인용문으로 부정 숨기기, 미지원 key의 강제 치환, 장소·조건 혼합 의도의 부분 성공을 검토하여 위 규칙에 반영했다. 모두 설계 제안이며 아직 구현되지 않았다.
